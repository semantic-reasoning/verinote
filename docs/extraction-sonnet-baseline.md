# Sonnet 승인 사전 추출: 최초 부분 기준선

> 이 문서는 최초 실행 당시의 기록이다. 이후 승인된 누락 표본 보완 및 현재 결정은 [보완 기준선과 A/B 판정 계약](extraction-sonnet-baseline-completed.md)에 있다. 아래 미완료·추가 승인 대기 표현은 최초 실행 시점에 해당한다.

2026-10-31에 사용자 승인으로 실제 Claude CLI를 호출했다. **#750은 미완료이며 열린 상태로 유지한다.** 세 모드 모두 관측 토큰 한도에 도달하여 계획한 자료별 3반복을 완료하지 못했다. 이 기록은 실제 호출의 부분 탐색 결과이며 최적화 채택 증거가 아니다.

## 실행 조건과 예산

- 코드: `11c2d79bf7f2de6bbc18639341972235563ab31a` (#749 구현 포함), Claude Code `2.1.311` (`claude --version`으로 확인).
- 요청 모델: 사용자가 지정한 `sonnet`. 실제 resolved model은 현재 benchmark export에 보존되지 않아 **미확인**이다. 같은 실제 모델 버전이었다고 단정하지 않는다.
- Python·패키지·OS: [environment.json](../benchmarks/extraction/results/750/environment.json).
- 자료: 버전 1의 short → long → dense → none → boundary, 각 3반복 계획. 매 문서 새 DB·사전·checkpoint. 별도 warm-up 없음.
- 순서: oneshot → document → batch. 호출당 timeout 90초, 사용량 누락 시 중단, 자동 재시도/모델 변경 없음.
- 전체 승인: 최대 90예약 요청, 1,800초, 관측 토큰 300,000. 각 모드는 최대 30요청·600초·100,000토큰과 전체 잔여 예산 중 작은 값으로 제한했다.
- 최초 oneshot이 token_limit으로 종료된 뒤 원본을 보존했다. 사용량 완전성·종료·cleanup 오류 부재를 확인하고, 재시도 없이 **다른 두 모드**를 전체 잔액 안에서 계속하도록 계획을 조정했다. 조정 사유와 시점은 [ledger.json](../benchmarks/extraction/results/750/ledger.json), 조정 전 상태는 [ledger-initial.json](../benchmarks/extraction/results/750/ledger-initial.json)에 있다.
- 재개 시 최초 UTC 시작 시각과 현재 시각의 차이를 반영한 뒤 monotonic 시계로 잔여 시간을 차감했다. 최초 1,800초 deadline을 연장하지 않았다. 시스템 시계가 불변이었다는 별도 검증은 없다.

총 **44예약 요청·302,172관측 토큰·408.832초**였다. 마지막 응답에서 전체 관측 한도를 **2,172토큰 초과**했고 이후 요청은 없었다. 토큰은 응답 후 집계하므로 승인 시 설명한 마지막 호출 초과가 발생했다. 전체 300,000 이내였다고 표현하지 않는다. 세 모드의 CLI 보고 비용 합은 **USD 1.0900573**, 사용량 확인은 44/44다. 이는 CLI 보고값이며 실제 계정 청구액을 확인한 것은 아니다. 종료·정리 시간도 있으므로 엄격한 wall-clock hard cap을 주장하지 않는다.

## 계획 대비 완료 범위

| 모드 | 계획 문서 실행 | 시작 | 성공·정답 통과 | 부분 실패 | 미시작 | 요청 | 관측 토큰 | CLI 보고 USD |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| oneshot | 15 | 9 | 9 | 0 | 6 | 12 | 101,801 | 0.4108988 |
| document | 15 | 12 | 11 | 1 | 3 | 16 | 100,293 | 0.3754181 |
| batch | 15 | 12 | 11 | 1 | 3 | 16 | 100,078 | 0.3037404 |

완료 문서 31개는 모두 정답 평가를 통과했다. 보정 요청과 cleanup 오류는 모두 0이다. document/batch의 마지막 실행은 세 번째 long이며, 첫 청크의 사용량 반영 후 예산 때문에 다음 청크가 허용되지 않았다. 각 1/2청크만 검증되어 recall 0.5, complete=false다. 모델 오답이나 완전 추출 성공으로 분류하지 않는다. none의 precision/recall은 정답·출력 관계가 없어 null이며 이를 1로 바꾸지 않았다.

원본에는 공통 표본 밖의 성공·부분 실패·비용도 모두 보존했다. 실행 자체의 종료 코드는 각 1이며 보고서 상태는 모두 stopped/token_limit이다. ledger의 partial_baseline은 세 모드의 시도가 끝났다는 의미이며 계획된 모든 반복이 완료됐다는 뜻이 아니다.

## 공통으로 완료한 자료 비교

세 모드 모두 완료한 `case_id × repetition`은 **9개**다: short/long/dense/none의 1·2회 및 boundary의 1회. [summary.json](../benchmarks/extraction/results/750/summary.json)에 정확한 키와 원본 값이 있다. 아래 값은 문서 반복 구간의 중앙값(초)이다. 자료 준비·평가가 포함되어 Service 접수–종료 지표와는 다르다.

| 자료 | 공통 표본 수/모드 | oneshot | document | batch |
|---|---:|---:|---:|---:|
| short | 2 | 18.594 | 5.232 | 4.682 |
| long | 2 | 33.178 | 8.946 | 6.303 |
| dense | 2 | 17.723 | 5.631 | 4.623 |
| none | 2 | 16.237 | 3.748 | 2.687 |
| boundary | 1 | 37.777 | 7.066 | 6.254 |

같은 공통 9문서에 귀속된 비용·토큰은 oneshot USD 0.4108988/101,801, document USD 0.2735567/73,193, batch USD 0.2227648/73,165다. 호출 순서·provider cache·실제 모델이 통제되지 않아 이 차이를 일반적인 절감률로 해석하지 않는다. 모드 전체 비용은 요청 수가 다르므로 그대로 비교하지 않는다.

문서별 시간에는 document/oneshot transport close가 포함되지만 batch 최종 close는 별도 `batch_teardown_seconds`와 전체 경과에 포함된다. 재사용 호출의 spawn 및 정상 exit는 null이다. PID 재사용은 provider cache 적중을 뜻하지 않는다.

## 관측한 병목과 해석 한계

성공한 모든 문서의 최초/보정 요청 구간 합을 해당 Service 접수–종료 시간 합으로 나누면 oneshot **99.953%**, document **99.815%**, batch **99.720%**다. 부모와 자식 시간을 다시 합하지 않았다. 이 비율은 CLI 호출·응답·기록 등 complete() 구간의 비중이며 모델 추론 전용 비율이 아니다.

batch 호출 16개에서 response_wait 중앙값은 **3.2599초**, reset 중앙값은 **0.0100초**다. process_observation은 시작 1·재사용 15다. document는 시작 12·재사용 4이며 oneshot v1은 persistent 관측 분류가 없어 unknown 12다. 단발 프로세스의 spawn 중앙값은 0.0034초로, 전체 호출 지연을 OS 프로세스 생성 시간만으로 설명하지 못한다.

이미 운영에 구현된 persistent 경로가 이 측정에서 짧은 지연을 보였지만, 다음 이유로 **프로세스 재사용의 인과적 개선율이나 신규 개선 성과를 주장하지 않는다**.

- 고정 순서에 따른 시간대·캐시 효과와 미확인 resolved model.
- oneshot과 persistent의 명령·설정 격리 차이.
- 계획된 3반복 미달, 자료별 1~3개 표본, 예산에 의해 잘린 불균형 표본.
- 단일 문서 순차 제출 시험이라 실제 다중 작업 큐 병목을 평가하지 못함.
- 실사용 사용자 문서가 아닌 작은 고정 합성 자료이며, 꼬리 지연·일반 품질 보장을 추정할 수 없음.

## 다음 후보와 미완료 작업

**최대 2청크 동시 처리(#752·#753·#754)를 다음 검증 우선 가설로 제안한다.** 운영과 가까운 batch에서도 요청 대기가 대부분이며 다중 청크 long/boundary를 순차 처리하므로 독립 호출의 대기를 겹칠 여지가 있다. 그러나 실제 동시 호출 지원, 두 worker의 초기화·캐시 비용, 품질·요금 영향은 측정하지 않았다. 로컬 검증/DB 최적화와 응답 간결화는 현재 근거만으로 우선 채택하지 않는다.

#750의 충분한 baseline 및 후보 선택 게이트가 완료됐다고 표시하지 않는다. 남은 baseline을 보완하고 실제 모델 식별 조건·실행 예산을 확정해야 한다. 현 승인의 관측 토큰 예산은 소진됐으므로 **추가 실모델 호출은 새 승인 전 수행하지 않는다**. 조건부 구현 이슈의 선행 조건도 완료로 바꾸지 않는다.

다음 A/B를 위한 사전 기준 **제안**은 다음과 같다. 현재 결과에서 검정력이 입증된 기준이 아니며, baseline 보완과 실행 승인 후 **새 호출 전에 확정**한다. 이번 자료에 소급 적용하여 최적화 채택으로 처리하지 않는다.

- 같은 revision·자료·사전·모델·prompt의 batch 수명에서 동시성 1과 2만 비교. 실제 모델 식별과 실행 설정을 남긴다.
- long/boundary 각각 10개 완전한 A/B 쌍, 자료별 AB/BA 각 5쌍을 사전 seed로 고정한다.
- 주 지표는 Service 접수–완료 시간. 자료별 paired 비율 중앙값 ≤0.80, 사전에 정의한 95% paired bootstrap CI 상한 <1.0을 제안한다. 추정법·seed·재표본 횟수는 호출 전 추가 확정한다.
- 완료율 100%, 정답·근거·금지 관계·인용 오류 회귀 0, 모델 오류·timeout·추가 보정 증가 0. 예산 중단 쌍을 성공 표본으로 바꾸지 않는다.
- 자료별 같은 paired 호출의 비용 및 입력+출력 토큰은 baseline의 110% 이하, 사용량 확인률 100%.
- short/dense/none 각 3쌍의 완료·품질 보존, 지연 중앙값 증가 10% 이하. long/boundary cold 시작 각 3쌍은 별도 기록하고 warm과 합치지 않는다.
- 승인된 고정 표본·예산에서만 수행하고 유리한 결과를 얻기 위한 추가 표본·자동 재시도는 하지 않는다. 실패율·꼬리 지연의 일반적 보장은 주장하지 않는다.

## 원본과 재현

[결과 폴더](../benchmarks/extraction/results/750/)의 세 report.json, stdout 요약 로그, ledger, 환경, 공통 표본 요약을 보존했다. [index.json](../benchmarks/extraction/results/750/index.json)에 파일별 SHA256과 크기가 있다. 원본 report는 수정하지 않았다. ledger의 argv는 실제 실행 인자이며 로컬 checkout 경로를 포함한다.

재현하려면 기록된 revision에서 패키지를 설치하고 ledger의 argv를 사용하되 Python/checkout 경로와 **새 결과 폴더**로 바꾼다. 기존 결과에 덮어쓰지 않는다. 세 모드의 한도를 독립적으로 초기화하지 말고 실제 요청·관측 토큰·전체 경과를 다음 모드에서 차감한다. unknown usage, 기록 손상, cleanup 오류 또는 전체 예산 소진이면 뒤 모드를 시작하지 않는다. 이번에는 사용량이 완전한 모드별 token_limit 종료만 이후 다른 모드 실행을 허용했다. 새 실험에는 별도 승인이 필요하다.
