# 생성 중 사전 이름·별칭 조정

이전 구간의 사전은 아직 승인되지 않은 초안이다. 이후 구간에서 새로운 근거를 찾으면 이름·타입·별칭 대상·관계 정의를 수정할 수 있다. 일반 추가와 기존 정의가 충돌하거나 한 응답 안에서 제안이 충돌해도, 검증 가능한 다른 항목과 다음 구간은 계속 처리한다. 이전 값을 잠정 유지한 경우도 이전 정의가 정답이라는 의미는 아니다.

## 명시적 수정

일반 `entities`, `aliases`, `relations` 배열은 새 항목을 담는다. 선택적 `revisions` 배열은 구간당 최대 40개이며 각 항목은 다음 형식이다.

```json
{
  "kind": "aliases",
  "key": "Response",
  "before": {"alias": "Response", "entity": "Old target"},
  "after": {
    "alias": "Response", "entity": "Correct target",
    "quote_ref": ["현재 구간의 시작 ID", "현재 구간의 끝 ID"]
  },
  "reason": "이후 원문이 별칭의 대상을 구체적으로 설명함"
}
```

`before`는 구간 시작 시점의 기존 정의 전체와 정확히 일치해야 하며 인용 필드를 넣지 않는다. `after`는 해당 종류의 전체 정의와 현재 구간의 `quote_ref`를 포함한다. 수정할 ID 또는 alias 자체는 유지한다. 표시 명칭·타입·별칭 대상·관계 설명/타입을 바꿀 수 있으며 새 항목을 revisions로 추가할 수는 없다. 이유만으로 근거 검증을 통과하지 않는다.

하나의 응답에 있는 revisions 전체는 하나의 트랜잭션이다. 예를 들어 개체의 표시 명칭을 바꾸면 기존 별칭 인용에 새 명칭이 없을 수 있다. 이때 해당 별칭의 새 근거도 같은 revisions에 넣어야 한다. 타입을 바꾸면 관계 타입도 유효해야 한다. 모든 의존 항목을 포함한 최종 사전이 기존 엄격 검증을 통과해야 적용한다. before 불일치, 중복 수정, 근거 부족, 의존 오류가 있으면 해당 수정 묶음을 보류하고 정상적인 새 항목은 유지한다.

## 정규 개체 통합

`초개인화`와 `Hyper-Personalization`을 각각 동일 타입 개체로 선언하고 원문 `초개인화 (Hyper-Personalization)`에 근거한 별칭 `Hyper-Personalization → 초개인화`를 제안한 경우, 중복 개체를 정규 개체의 별칭으로 통합할 수 있다. 같은 응답의 중복과 이전 구간의 중복 모두 적용된다.

별칭의 시작과 대상이 선언된 개체이고, 타입이 같으며, 인용에 양쪽 표시 명칭이 있어야 한다. 연결된 제안들을 함께 검증하며 시작 개체 제거, 별칭 추가, 그 개체를 가리키던 기존 별칭의 대상 조정을 함께 반영한다. 기존 별칭의 인용을 임의로 바꾸지 않는다. 최종 이름을 뒷받침하지 못하는 인용·순환·경쟁 대상·동시에 제안한 명시적 수정과의 충돌이 있으면 통합을 보류한다. 문자열 유사성이나 번역 추측만으로 합치지 않는다. 별칭이 대상 개체의 ID·이름이나 같은 개체의 다른 별칭과 공백(스페이스·탭·줄바꿈, 런 폭 차이 포함)만 다르거나, 통합되는 개체의 이름이 대상과 공백만 다르거나, 같은 대상으로 통합되는 다른 개체의 이름이나 대상의 별칭과 공백만 다르면 통합하지 않는다. 개체 자신의 ID와 이름이 공백만 다른 개체 행은 거부하지 않으며(#828), 통합할 때 통합되는 개체나 대상 자신의 그 쌍은 서로 비교하지 않는다. 통합되는 개체의 이름은 별칭 표기와 달리 ID로 해석되지 않으므로, 대상 자신의 이름이나 ID와 정확히 같은 이름은 대상의 ID·이름 중 다른 쪽과 공백만 달라도 통합을 막지 않는다. 별칭이 대상의 `name`과 정확히 같으면 유지한다. 단, 그 `name`이 대상의 ID와 공백만 다르면 그 별칭은 ID와 공백만 다른 표기이므로 제외한다.

## 공백만 다른 표기

모델이 제안한 별칭, 같은 타입 개체의 통합, `revisions`로 별칭을 옮기거나 대상 이름을 바꾸는 변경, 정규 개체 이동으로 기존 별칭이 공백만 다른 개체에 붙는 경우, 같은 개체의 두 별칭이 공백만 다른 경우는 모두 공백만 다른 표기를 연결하게 되므로 받아들이지 않는다. 공백 차이가 그 행에서 바로 드러나는 별칭과 통합 제안은 그 행만 `alias_spacing_only`로 제외하고 나머지 제안은 따로 처리하며, 여러 행이 함께 통합되어야 드러나는 경우와 `revisions`는 묶음 전체를 보류한다. 같은 묶음에 속해 함께 보류된 행은 그 자체에는 공백 차이가 없을 수 있으며, 이유는 묶음에 공백만 다른 쌍이 있다고 밝히고 그 행에서 공백 차이를 찾으라고 하지 않는다. 띄어쓰기는 한국어에서 뜻을 바꿀 수 있어 같은 대상인지는 사람이 판단한다. 공백을 뺀 비교는 거부에만 쓰며 표기를 찾거나 제안하거나 연결하는 데는 쓰지 않는다. 이전 구간에서 이어받은 기록이 이미 가진 연결은 새 제안이 아니므로 관련 없는 제안을 보류시키지 않으며, 그 별칭을 그대로 다시 제안해도 제외하지 않는다. 이어받는 schema 1·2 기록은 이 규칙으로 다시 검사하지 않아 그 연결이 초안에 남을 수 있다. 이미 가진 연결을 다른 대상으로 옮기는 제안은 새 연결로 본다. 사람이 사전을 수정해 추가하는 경로는 막지 않는다. 추출 점검의 **사전에 추가** 경로도 그중 하나이며, 정확히 일치하는 표기만 찾고 공백을 뺀 비교를 쓰지 않는다. 인용에 개체 이름이 없으면 사람의 판단을 별칭 행의 `judged_alias`·`judged_entity`·`judged_name`으로 기록해 이름을 고정한다. 범위 밖(#828): 개체 행의 ID와 이름이 공백만 다른 경우, 추출 시점의 연결, 그리고 이름으로 통합된 개체의 이름과 공백만 다른 표기가 이후 청크에서 같은 대상에 들어오는 경우. 마지막 경우에는 먼저 통합된 개체의 이름이 사전에 남지 않으므로 사전만으로는 감지할 수 없고, 이 검사가 그것까지 막는다고 볼 수 없다. 같은 응답 안의 경우와, 먼저 들어온 표기가 별칭이나 ID로 사전에 남아 있는 경우는 막는다(이름만 남았다 사라지는 경우를 #828에서 다룬다). 또 이 비교는 공백(`str.split` 기준)만 다루며 길이가 없는 문자와 유니코드 정규화 형식 차이는 같은 표기로 보지 않으므로 그런 표기는 막지 않는다.

## 승인 전 검토

실행과 사전 화면의 **사전 조정**에서 적용/보류 건수, 변경 전 정의, 제안과 원문 인용, 이유를 확인할 수 있다. 표시된 양쪽 정의는 생성 당시 상태이며 사용자가 이후 편집한 현재 사전과 다를 수 있다. 상세는 처음 20건이며 전체 건수와 생략 건수는 별도로 표시한다. 누락·손상된 기록과 이전 방식에서 재사용한 구간은 미확인으로 표시한다.

동일성 제안과 원문 동시 출현은 검토할 근거이며 의미가 같다는 자동 증명이 아니다. 최종 사전은 계속 검토 대기로 저장된다. 보류된 대안은 기존 내용 수정 기능으로 반영한 뒤 승인할 수 있다(조회 참조 접두사로 시작하는 새 개체 ID·별칭과 줄바꿈·탭이 든 새 개체 ID는 제외). 기존 승인 사전·추출 snapshot·과거 실행은 바꾸지 않는다. 근거 부족 항목의 제외 집계는 조정 집계와 별도로 유지하며, 제외된 충돌 행이 보류 조정에도 나타날 수 있으므로 두 건수를 합쳐 변경 개수로 해석하지 않는다.

## 저장·복구

checkpoint schema 3은 사전, 완료 offset, 제외 내역, 조정 내역을 원자적으로 저장한다. 이 저장이 성공한 뒤 진행률과 메모리 상태를 확정한다. 실패하면 해당 구간을 확정하지 않고 이전 prefix를 유지한다. 추가 보정 호출이나 자동 재전송은 없다. 재시도는 호환되는 마지막 저장된 prefix에서 이어가며 기존 조정 건수를 중복 합산하지 않는다. 현재 생성 필터는 v6이며, 일반 행에서 `quote_ref`만 누락되면 근거를 만들지 않고 `reference`로 제외한다. 다른 필수 필드·추가 필드·명시적으로 제공된 잘못된 참조와 `revisions`의 검증은 유지한다. 기존 v5의 검증된 schema 3 prefix는 재사용하고 새 기록은 v6으로 저장하며 이전 파일은 변경하지 않는다. v4 이하 또는 알 수 없는 정책으로 저장된 schema 3 prefix는 호환되지 않아 버리고, 호환되는 다른 기록이 없으면 모든 구간을 처음부터 다시 호출한다. 실패한 생성의 이미 지불한 호출을 다시 지불하는 비용이 있다.

schema 1·2는 정책·프롬프트 허용 목록, 원문·실행·모델·HTTP 옵션·재생성 대상·완료 경계 및 사전을 다시 검사한 뒤 읽는다. 직전의 기존 정의 고정 프롬프트와 그 이전 개수 한도 설명 프롬프트를 명시적으로 허용한다. 기존 기록은 수정하지 않고 새 실행에 schema 3으로 저장한다. 새 기록은 이전 코드에서 재사용할 수 없지만, 이전 파일은 그대로 남아 있다. SQLite 마이그레이션·기존 승인 데이터 backfill은 없다.

조정 감사 기록은 최대 4 MiB, 전체 checkpoint는 최대 30 MiB다. 호출별 일반 행 한도·현재 원문 근거·사전 전체 24 MiB 제한은 유지한다. 정의60,000바이트는 저장 거부 기준도 실행 거부 기준도 아니며 전송 형식을 고르는 사용자 설정 기준의 기본값이다. 기준을 넘는 문맥은 정의를 삭제하지 않고 무손실 표로 전송하되, 표도 기준을 넘거나 표가 전체 요청에 들어가지 않으면, 전체 요청에 들어가는 더 작은 쪽 형식을 전송한다. 실제 전체 요청 한도는 별도로 검사한다. 구조가 잘못된 응답, 알 수 없는 일반 별칭 대상, 크기 초과, 통신 오류는 중단한다. 관계의 미선언 타입은 기존 제외 정책을 따른다.

검증: `python -m unittest discover -s tests -p 'test_dictionary*.py'` 및 `python -m unittest discover -s tests -p test_alias_conflicts.py` 및 `python -m unittest discover -s tests -p test_spacing_links.py`. 가짜 모델 응답으로 수정 묶음, 통합, 충돌 보류, 저장 실패, 이전 prefix 재사용과 승인 분리를 확인한다.
