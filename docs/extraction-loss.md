# 승인 사전 기반 추출의 손실 점검

새 관계 추출은 계약 3을 사용합니다. 기존 계약 0/1/2 실행과 원문·사전·승인 이력은 변경하지 않습니다. 이전 방식으로 성공한 같은 사전 revision도 새 방식으로 한 번 다시 추출할 수 있습니다. 기존 후보를 덮어쓰지 않으므로 중복 후보는 승인 전에 검토해야 합니다. 연구용 벤치마크는 비교 조건을 유지하기 위해 명시적으로 계약 2를 사용합니다.

각 청크의 초기 응답, 사전 불일치와 인용 미확인 후보, 전체 인용, 원문 위치, 원래 응답 행 번호와 응답 hash를 손실 점검 기록에 보존합니다. 원문 위치 확인은 인용 문자열이 해당 구간의 한 위치에서 발견되었다는 뜻이며 관계의 의미적 타당성을 증명하지 않습니다. 사전에 없는 개체·관계나 허용되지 않는 타입은 일반 관계 후보로 저장하거나 그래프에 넣지 않습니다. 사전 수정·재승인과 새로운 추출·후보 승인은 별도 작업입니다.

초기 검증 이후 관계가 0개인 청크는 승인 사전과 원문을 다시 제공하여 누락된 직접 관계를 보충 점검합니다. 청크당 최대 1회, 동일 문서 버전·사전·모델·실행 조건의 재시도 전체에서 최대 4회를 원문 순서대로 허용합니다. 각 보충 응답은 최대 20개이며 기존 80개 사실·제외 항목 합산 한도를 넘지 못합니다. 빈 결과도 정상입니다. 80개 한도에 도달한 구간, 관계가 0개인 구간, 모든 관계가 no_evidence인 구간은 각각 점검 신호로 남습니다. 보충 호출은 관계가 0개인 구간에만 적용하므로 다른 신호는 자동 보충을 뜻하지 않습니다.

보충 호출은 비용이 추가될 수 있습니다. 기존 청크의 남은 360초, 입력 문맥·출력 제한, 취소 및 병렬 실패 차단을 공유하며 새 제한 시간을 받지 않습니다. 보충 응답의 잘못된 객체 형식이나 개수 초과는 청크 실패입니다. 개별 후보의 사전 불일치·인용 미확인은 손실 기록에 남기고 정상 후보와 분리합니다. 승인 어휘로 정규화한 주어·관계·목적어·인용이 모두 같은 보충 후보는 한 번만 추가합니다. 보충 결과를 반영한 coverage는 로컬 집계라고 표시하고 초기 모델 판단은 손실 기록에 보존합니다.

보충 응답의 사전 불일치 후보는 주어·목적어별 사전 판정 정보가 없어 **사전에 추가 / 타입 고치기** 단축 버튼을 제공하지 않습니다. 첫 응답의 제외 목록과 별도로 보존되므로 관계별 추출 점검의 제외 건수와 타입 수정의 영향 수에는 포함되지 않습니다. 원문 위치 확인 여부에 따라 손실 점검의 **원문 위치 확인된 미해결** 또는 **인용 미확인**으로 집계됩니다. 원문과 후보를 대조하고 문서의 사전에서 **내용 수정 → 재승인 → 승인 사전으로 추출 → 새 후보 검토** 순서로 개체·별칭이나 관계 정의를 바로잡으세요. 사전 수정만으로 기존 후보가 저장·승인되지는 않으며, 재추출은 추가 호출·비용이 들 수 있고 후보 복원을 보장하지 않습니다.

보충 호출 전에 `runs/<id>/recovery-attempts.json`에 예약을 필수 저장합니다. 중단·취소·응답 불확실 이후에도 해당 청크의 예약은 소모된 것으로 취급하고 반복 호출하지 않습니다. 이전 호환 실행의 예약 기록이 없거나 손상되었으면 추가 보충은 `budget_unknown`으로 건너뜁니다. 일반 추출은 진행할 수 있으나 완전한 점검으로 표시하지 않습니다. 한도 초과, 이전 시도, 남은 후보 용량 없음도 서로 구분합니다.

청크별 `loss-audit.json`(최대 2 MiB)과 `extraction-checkpoint.json`(최대 18 MiB)에 같은 감사 데이터를 저장합니다. 계약 3에서는 이 필수 기록의 쓰기 실패가 후보 공개를 막습니다. 재개 시 원문·사전·실행 계약, 감사 hash와 내용을 확인하며, 누락·손상된 감사가 있는 접두 구간은 재사용하지 않습니다. 재사용한 감사는 새 실행 아래에도 복사하고 기존 실행 파일은 보존합니다. 계약 2의 선택적 checkpoint 동작은 유지합니다. SQL 마이그레이션이나 자동 데이터 backfill은 없습니다. 배포 롤백 시 기존 실행 자료를 삭제하지 말고 계약 3 자료를 보존해야 합니다. 구버전은 계약 3 실행을 읽거나 재개할 수 있다고 보장하지 않습니다.

실행 상세의 손실 점검에는 초기·보충 후보 수, 원문 위치가 확인된 미해결 후보, 인용 미확인 후보, 최종 관계 0개 구간, 보충 완료·미실행 구간을 구분합니다. 처리 완료, 모델의 no_evidence, 보충 완료는 누락 없음의 증거가 아닙니다. 미해결만 있는 실행은 기존 게시 조건에 따라 실패할 수 있으며 감사 기록은 계속 조회할 수 있습니다. 보존 기록이 없으면 미해결 0개가 아니라 점검 불가로 표시합니다.

검증은 합성 문서와 가짜 호출자로 수행합니다. 실제 모델의 recall 개선율이나 의미 정확도는 별도의 원문 정답 검토가 필요합니다. 문장 간·청크 경계 관계, 사전 자체의 표현력 부족, 모델이 처음부터 제안하지 않은 관계는 여전히 누락될 수 있습니다.
