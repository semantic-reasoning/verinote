# #826 Ollama 입력 한도 27,648바이트 측정

측정만 했다. `input_byte_limit`, 옵션, 계약 문서는 바꾸지 않았다. 원본 근거는 `environment.json`과 `calls/`
(호출마다 `NN-prompt.txt`, `NN-response.json`, `NN.json`)에 있다. 도구는 `verinote/diagnostics/ollama_input_limit.py`이고
예산(사용자 승인): 로컬 호출 20회, 약 1시간.

## 조건

- 모델 `qwen2.5:7b`, 다이제스트 `845dbda0ea48ed749caafd9e6037047aa19acfcfd82e704d7ca97d631a0b697e`, Ollama 0.40.16.
- `num_ctx` 32768, `num_predict` 4096, `temperature` 0, `format` json (제품 기본값). `num_ctx - num_predict` = 28,672토큰.
- 프롬프트: 제품의 추출 지시문(계약 3)과 사전 생성 지시문에 같은 구조의 입력(JSON)을 붙였다. 사전은 개체 2·관계 1의 작은 것이다.
  원문은 한글 위주(`docs/architecture.md`)와 ASCII 위주(표준 라이브러리 `argparse.py`·`typing.py`)를 크기에 맞춰 잘라 썼다.
  프롬프트 끝에 `END-…` 표식을 넣고 응답 JSON의 `end_marker`로 되돌리게 했다.
- 크기(UTF-8 바이트): 8,192 / 27,648 / 40,960 / 81,920 / 122,880. 크기마다 호출 1회, 반복 없음.
  제품 경로는 27,648바이트를 넘으면 호출하지 않으므로, 이 측정은 제품 거부를 우회해 `/api/generate`를 직접 호출했다.

## 바이트당 토큰 (`prompt_eval_count` / 프롬프트 UTF-8 바이트)

| 단계 | 입력 | 8,192 | 27,648 | 40,960 | 81,920 |
|---|---|---|---|---|---|
| 추출 | 한글 | 0.272 | 0.278 | 0.277 | 0.277 |
| 추출 | ASCII | 0.249 | 0.235 | 0.234 | 0.226 |
| 사전 생성 | 한글 | 0.266 | 0.332 | 0.337 | 0.340 |
| 사전 생성 | ASCII | 0.272 | 0.359 | 0.348 | 0.377 |

122,880바이트의 4회는 비율로 쓰지 않는다. 추출·한글은 31,758토큰(응답이 `length`로 끝나 JSON이 아님), 추출·ASCII는 26,986토큰
(정상), 사전 생성 2회는 모두 16,386토큰이다. 16,386은 입력이 컨텍스트에서 잘렸다는 뜻으로 읽히지만(`prompt_eval_count`가 입력 크기에
비례하지 않는다) 어느 부분이 잘렸는지는 알 수 없다. 표식은 응답에 돌아왔으므로 프롬프트 끝은 남았다. 그러나 두 호출의 응답에는 `end_marker`만 있고 사전 스키마 키(`entities`, `aliases`, `relations`)가
없어 지시문(프롬프트 앞부분)이 유실된 것으로 보인다. 이 두 호출은 입력 전체가 들어갔는지 알 수 없으므로 "들어감" 판정과 비율에서 제외하고 `analysis.json`에서 `fits_budget`을 `null`로 둔다(원본 `calls/15.json`, `calls/20.json`의 `fits_num_ctx_minus_num_predict: true`는 토큰 수만 본 값이다).
모델과 입력 종류별로 따로 적었고 하나의 일반 비율로 합치지 않았다. 사전 생성은 추출보다 바이트당 토큰이 높게 측정됐다(원인은 검증하지 않았다).

## `num_ctx - num_predict`(28,672토큰) 안에 들어간 가장 큰 크기

| 단계 | 입력 | 가장 큰 측정 크기 | 토큰 |
|---|---|---|---|
| 추출 | 한글 | 81,920 | 22,685 |
| 추출 | ASCII | 122,880 | 26,986 |
| 사전 생성 | 한글 | 81,918 | 27,831 |
| 사전 생성 | ASCII | 40,960 | 14,250 |

사전 생성·ASCII 81,920바이트는 30,844토큰으로 28,672를 넘었는데도 호출은 정상 완료됐다(`done_reason` stop, 표식 반환).
`num_ctx` 32,768 안에는 들어갔기 때문이다. 즉 입력 한도는 `num_ctx - num_predict`를 지키려는 것이다. 122,880바이트 호출의 잘림은 `prompt_eval_count`와 응답 형태로 추정할 뿐
입력 잘림의 직접 증거는 아니며, 원인은 알 수 없다.

## 응답 상태

20회 중 3회(번호 2, 5, 17)가 `done_reason` `length`로 끝나 JSON이 아니었다. 번호 2와 17은 입력이 한도 안인데도 출력이 4,096토큰에 닿았다
(입력 크기가 아니라 출력 반복으로 보이나 원인은 확인하지 않았다). 번호 5는 입력 31,758토큰이다.
나머지 17회는 JSON이 유효했고 표식이 돌아왔다. 이 중 15회는 단계별 최상위 스키마 키를 모두 갖췄고, 번호 15와 20은 `end_marker`만
돌려줘 스키마 키가 없다(위 참고). 키 검증은 `python3 -m verinote.diagnostics.ollama_input_limit --analyze <폴더>`가 저장된
응답에서 오프라인으로 계산해 `analysis.json`에 둔다. 제품의 응답 검증(`parse_response`, 인용·`quote_ref` 검증)은 적용하지 않았으므로 제품 기준 응답 유효성은 **알 수 없음**(`analysis.json`의 `product_validation`: `not evaluated`)이다. 최상위 키 존재는 제품 검증이 아니다.

## 결론과 한계

- 이 모델에서 측정한 바이트당 토큰은 0.226–0.377이다(122,880바이트 호출 제외). 입력 한도 27,648바이트는 최악 비율(0.377)로도 약 10,400토큰이어서
  28,672토큰 예산의 약 36%만 쓴다. 이 모델의 데이터는 한도가 보수적이라는 것을 보여 주지만, **한도 값을 바꿔야 한다고 지지하지는 않는다.**
- 외삽(추정이며 측정값이 아님): 측정한 비율이 크기와 무관하게 유지된다고 가정하면 `num_ctx - num_predict` 안에 들어가는 크기는
  사전 생성·ASCII 약 76,000바이트(28,672 / 0.377), 추출·한글 약 103,000바이트(28,672 / 0.278)다. 측정으로 확인된 최대 크기는 위 표다. 다른 모델(토크나이저)은 측정하지 않았다. 모델 범위가
  넓은 한도 값은 이 자료로 정할 수 없다.
- 한계: 모델 1개, 크기당 1회, 합성 사전 1종, 제품 응답 검증 미적용, 122,880바이트 호출의 잘림 위치 미확인. 한도 변경은 별도 이슈로 다룬다.
