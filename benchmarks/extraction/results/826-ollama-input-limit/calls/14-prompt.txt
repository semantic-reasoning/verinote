개체 id는 문서 간에도 의미 있는 정규 명칭을 사용하세요. e1 같은 임의 번호는 금지합니다. 원문에 공식 ID가 있으면 우선 사용하세요.

별칭은 원문이 동일 개체라고 명시하는 경우만 선언하세요. 개체 ID 자체를 별칭으로 반복하지 마세요. 자기 자신을 가리키는 매핑은 사전에 추가되지 않습니다. 문자열 유사성, 약어 추측, DB와 서비스 혼동은 금지합니다.
관계 정의에는 방향과 타입, 조건·부정·시점·설계 가정의 처리, 제외 대상을 명시하세요. 내부 서비스 직접 호출 의존은 depends_on, 서비스 운영 책임은 owned_by처럼 일관된 이름을 제안하세요. 문서 담당자와 서비스 소유자는 다릅니다. API 호출과 API 소유 서비스도 구분하세요.
관계의 subject_types와 object_types는 기존 dictionary.entities와 이번 응답 entities의 type 값만 사용할 수 있는 비어 있지 않은 배열입니다. 각 문자열은 선언된 type과 정확히 일치해야 합니다. 개체 id나 name을 넣거나 상위·유사 타입을 추측해 추가하지 마세요. 별도의 타입 선언이나 타입 상속은 지원하지 않습니다.
예: 개체 타입에 '도서', '사람', '회사'만 있으면 authored_by의 subject_types는 ['도서']이며 ['도서','저작물']은 잘못된 값입니다. 고용 관계의 object_types도 ['회사']이며 ['회사','조직']은 잘못된 값입니다. 이전 타입이 잘못되었다면 아래 revisions로 의존 관계와 함께 조정을 제안하세요.
출력 전 모든 관계의 양쪽 타입이 기존·신규 개체에 실제 선언되어 있는지 확인하세요. 필요한 개체가 이번 원문에 있으면 정확한 name과 quote_ref를 갖춘 개체로 선언하세요. 타입을 맞추기 위한 가짜 개체는 만들지 말고, 근거 있는 개체 타입으로 표현할 수 없는 관계는 제안하지 마세요.
특허·기술 문서의 구성요소·상태 등 나열된 개체는 빠뜨리지 마세요. 이 사전은 사람이 수정·승인한 뒤 사용합니다.
기존 dictionary는 아직 승인되지 않은 잠정 초안이며 항상 옳지 않습니다. 일반 배열에는 새 항목만 반환하고 기존 정의의 수정은 선택적 revisions 배열에 명시하세요. 추가·수정이 없으면 빈 배열을 반환하세요. 같은 정의를 인용만 바꿔 반복하지 마세요.

entities의 name·type, aliases의 대상 entity, relations의 정의·타입을 수정할 수 있습니다. 개체 이름·타입을 바꾸면 기존 별칭 인용과 관계 타입도 맞아야 합니다. 필요한 기존 별칭·관계 조정을 같은 revisions 묶음에 모두 제안하세요. 앱은 묶음 전체를 검증한 뒤 적용하고, 의존 근거가 부족하면 조정을 보류하며 다른 구간은 계속 처리합니다.
정규 ID를 통합하려면 정규 대상 개체를 선언하고 기존 ID를 대상으로 향하는 별칭으로 명시하세요. 예: 동일 개념의 초개인화와 Hyper-Personalization을 별개 개체로 만들었다면, 양쪽 이름이 함께 있는 원문 근거로 {"alias":"Hyper-Personalization","entity":"초개인화","quote_ref":[...]}를 제안할 수 있습니다. 앱은 동일 타입·양쪽 이름의 근거·기존 별칭 참조가 유지될 때만 중복 개체를 별칭으로 통합합니다. 서로 다른 개체·타입·동음이의어를 추측하여 합치지 마세요. 같은 항목을 revisions와 ID 통합으로 동시에 조정하지 마세요.
충돌 제안을 아무 설명 없이 덮어쓰지 마세요. 앱은 적용한 조정과 보류한 양쪽 정의·근거를 승인 전 검토용으로 남깁니다.
sources는 원문의 연속 구간입니다. quote_ref에는 이번 sources에 있는 시작·끝 id 문자열을 순서대로 넣으세요. 한 구간이면 같은 id를 두 번 쓰세요. 앱이 그 범위의 원문을 그대로 복원합니다. quote 문자열이나 문자 위치를 생성하지 마세요. name은 선택 구간에 그대로 있어야 하며 별칭 구간에는 alias와 정규 name이 모두 있어야 합니다. 가능한 짧고 충분한 구간을 고르세요.
