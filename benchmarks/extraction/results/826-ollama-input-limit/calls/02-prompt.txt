동시성 토큰이다. 따라서 과거 버전도 명시적으로 검토할 수 있지만 도중의 새 버전 등록·삭제·롤백은 충돌로 처리한다. 빈 배치, 중복, 잘못된 타입(bool revision 포함), 추가 필드, 다른 문서/버전의 항목, 사전 및 pending이 아닌 항목은 거부한다.\n\n문서 토큰·멤버십·revision·상태 검사와 각 후보 검증·상태 변경·이력 기록은 하나의 `BEGIN IMMEDIATE` 안에서 실행한다. 개별 `review`와 공유하는 `_review_item`이 원문 인용과 추출 당시 고정 사전을 다시 검증하며, 하나라도 실패하면 앞선 변경과 events까지 모두 롤백한다. 성공하면 항목별 revision이 한 번 증가하고 같은 검토자/이유로 개별 승인 이벤트를 기록한다. 현재 사전의 승인 철회를 이미 추출된 사실의 승인 금지로 바꾸지 않는다. 개별 검토와 동일한 계약이다.\n\n브라우저는 초기 선택을 비우고 pending page/fact에만 체크박스를 표시한다. 전체 선택은 한도를 넘어도 몰래 잘라내지 않고 한도 초과를 표시한다. 확인창을 열 때 문서 ID·표시 버전·문서 토큰·선택 ID/revision을 별도 객체에 고정한다. 전송 중에는 중복 제출을 막고, 충돌 시 사용자가 새로고침해서 다시 선택한다. 늦게 도착한 문서 응답은 요청 순서로 차단하며 승인 완료 후에도 같은 문서/버전을 보고 있을 때만 해당 화면을 갱신한다. 모델 호출이나 DB 스키마 변경은 없다.\n\n## 채택한 범위\n\n첫 원자적 구현 단위는 버전별 문서 등록 → 실제 CLI 추출 → 사람 검토 → Wirelog 결과와 원문 증명이다. 기존 교육자료의 서비스·문서명·승인 예시를 하드코딩하지 않는다. 복수 사용자 인증, 전역 온톨로지 병합, OCR, 의미 검증 자동화는 이 초기 구현 범위에 포함하지 않는다.\n\n## 자연어 질문\n\n`assistant.py`는 `query_graph`, `search_knowledge`, `read_wiki`, `search_documents`, `read_document`만 허용한다. 실제 graph 실행 없이 최종 답변할 수 없다. graph/wiki/source/inference와 실제 증거 ID를 대조하며 빈 graph는 긍정 근거가 아니다. 승인 사전 검색은 문서별 어휘 안내이고 인용 근거가 아니다. `read_wiki`는 고정 페이지의 주장과 원문 인용을 렌더링한 문자열을 2,000자씩 제공하며 page_id/revision/version/sha256, claim_indices, offset/end_offset/next_offset/partial을 기록한다.\n\nAssistant 초기화는 고정 메타데이터만 사용한다. 과거 스냅샷에 메타데이터가 없을 때도 Store.document_metadata가 버전별 컬럼만 조회하며 원문이나 현재 승인 항목을 읽지 않는다. 원문은 authorize_source를 통과한 뒤 source_text로 지연 로딩한다. search_documents 기본 mode=metadata는 제목·파일명만 검색하며 mode=body는 document_id와 fallback이 필수다.\n\nfallback은 lookup_id, reason, detail, wiki_evidence_ids로 구성한다. reason은 legacy_snapshot/no_approved_wiki/no_match/insufficient_wiki 중 실제 상태와 일치해야 한다. 해당 문서를 포함한 잘리지 않은 search_knowledge 결과 및 graph 결과가 이전 모델 입력에 전달되어야 한다. 관련 위키가 있으면 검색된 각 페이지의 읽기 근거도 이전 회차에서 전달되어야 한다. 같은 tools 배열에서 추측한 근거 ID로 우회할 수 없다. 거부 요청도 trace에 error로 남고 원문 조회는 발생하지 않는다. 검사는 순서·범위만 보장하며 검색어와 의미적 충분성은 모델 판단이다. 부분 위키 읽기 범위를 명시하고 이를 전체 부재로 표현하지 않도록 요청한다.\n\n새 스냅샷 pages/ontologies는 facts 및 documents와 동일 트랜잭션에서 승인된 현재 버전 내용만 고정한다. 기존 스냅샷의 누락 필드를 최신 데이터로 채우지 않는다. 자연어 질문에서만 문서 100/사실 500/위키 500/사전 100개와 지식 8 MiB 한도를 적용하며 직접 그래프 조회 한도는 바꾸지 않는다. 검색 20개/위키·원문 읽기 2,000자/결과 30,000바이트/프롬프트 60,000바이트, 모델 6회·도구 10회 예산을 유지한다. 잘린 지식 검색으로 fallback을 허용하지 않으므로 검색 범위를 좁혀야 한다. 삭제는 기존 documents 참조를 따라 새 지식 payload를 포함한 스냅샷 전체와 관련된 읽을 수 있는 질문을 제거한다(읽을 수 없는 질문 행은 아래 삭제 규칙대로 남는다).\n\n`questions` 테이블은 제출 시 고정한 snapshot, agent/model, 질문, 상태, 누적 trace/evidence, 답변과 오류를 저장한다. 검색·읽기는 snapshot의 문서 버전만 사용하고 그래프는 snapshot의 승인 payload만 사용한다. 사전 생성 2개·승인 사전 기반 추출 2개와 별도로 질문은 1개씩 실행하며, 대기·실행 합계 8개 슬롯은 함께 사용한다. 재시작 시 미완료 질문도 interrupted로 복구하고, 취소 중(cancelling)이던 질문은 cancelled로 복구한다. 이때 cancelled·interrupted·error로 저장된 질문(이전에 그렇게 저장된 질문 포함)의 running·analyzed 분할 처리 회차(`context_processing`)는 각각 cancelled·interrupted·failed로 바꾸며, 바뀌는 내용이 없는 질문 행은 다시 쓰지 않는다. 복구가 읽을 수 없는 질문 행(엄격한 UTF-8이 아님, JSON이 아님, JSON 객체가 아님, status가 queued·running·success·error·interrupted·cancelling·cancelled가 아님, id·question·agent·model·snapshot·created_at 중 없거나 문자열이 아닌 항목이 있음, 저장된 id가 행 ID와 다름, 행 ID가 엄격한 UTF-8 텍스트가 아님(BLOB·NULL 포함), 회차 항목이 객체가 아님, 너무 깊게 중첩되어 읽을 수 없음)이나 바꾼 내용을 UTF-8 텍스트로 저장할 수 없는 행은 건너뛰고 쓰지 않으며 나머지 행은 그대로 복구한다. 건너뛴 행은 저장된 내용을 그대로 유지한다. 질문 API의 읽기 경로(`question`, `questions`, `unreadable_questions`, `cancel_question`, `queue_rows`, `usage_owners`, `delete_document`)는 복구와 같은 계산(`question_job`)으로 행을 분류하며, 읽을 수 없는 행을 처리 중·취소 중으로 읽지 않는다. 작업자가 쓰는 `save_question`·`finish_question_cancel`·`end_unstored_question`은 그대로 `json.loads`를 쓰며, 실행 중에 행이 손상될 때만 이 경로에 닿는다. 목록(GET `/api/questions`)은 이런 행을 빼고 읽을 수 있는 최근 30개를 반환하고, GET `/api/questions/unreadable`은 개수 제한 없이 rowid 순서로 32자리 소문자 16진수 텍스트로 저장된 ID 목록과 그 밖의 ID 수(`hidden`, BLOB으로 저장된 ID 포함)를 반환한다. 상세 조회와 취소는 409로 거부하고, 대기열 항목은 `unreadable: true`로 표시하며, 사용량 집계는 빼되 전체 작업 수에는 센다. 문서 삭제는 이런 행을 진행 중 확인에 넣지 않고, 어느 스냅샷의 것인지 읽지 않으므로 지우지 않으며 `unreadable_questions_kept`로 수를 반환한다. 스냅샷·조회 기록도 `typeof`/`CAST AS BLOB`으로 읽어 읽을 수 없는 행(JSON 객체가 아님, `documents`나 `snapshot`이 없거나 형식이 다름, 삭제 대상 문서의 항목에 정수 `current_version`이 없음, ID가 텍스트가 아님)이 삭제를 실패시키지 않는다. 읽을 수 없는 스냅샷·조회 기록과 그 스냅샷을 가리키는 읽을 수 있는 질문·조회 기록은 지우지 않고 `unreadable_snapshots_kept`·`unreadable_queries_kept`·`questions_kept_with_snapshot`·`queries_kept_with_snapshot`로 수를 반환한다(ID가 텍스트가 아닌 스냅샷이 있으면 어느 스냅샷에도 속하지 않는 `snapshot`을 가진 기록을 그 스냅샷을 가리키는 것으로 센다). `queries()`는 읽을 수 없는 행(위 형식에 더해 질의 결과 형식(`status`가 success·empty·ambiguous, 문자열 `snapshot`·`engine`, `[주어, 관계, 목적어]` 문자열 목록인 `rows`, 그런 `row`와 문자열 `fact_ids`를 가진 `proofs`, 문자열 `id`와 객체 `payload`를 가진 `facts`)이 아니거나, `query`에 알 수 없는 키나 문자열·null이 아닌 값이 있거나, NaN·무한대(`1e999` 포함)나 UTF-8로 보낼 수 없는 값이 있는 행)을 빼고 읽을 수 있는 최근 30개를 저장된 전체 결과 그대로 반환한다. `unreadable_queries()`(GET `/api/queries/unreadable`)는 개수 제한 없이 그런 행의 수를 반환한다. 같은 바이트의 텍스트 ID 스냅샷과 BLOB ID 스냅샷이 있으면 그 이름을 가리키는 질문·조회 기록은 모호하므로 지우지 않고 센다. `snapshot()`은 같은 ID의 저장 행이 현재 내용의 정규 JSON과 바이트 단위로 다르면 같은 내용으로 다시 쓴다. 복구는 이런 행을 쓰지 않으며, 지우는 경로는 사용자가 요청하는 POST `/api/questions/{id}/delete-unreadable`(정확히 `{}`, 32자리 소문자 16진수 id)뿐이다. 이 경로는 같은 쓰기 트랜잭션에서 다시 판정해 읽을 수 있는 행은 409로 거부하고 로그 정리 의무를 함께 저장한다. 복구와 전체 행을 읽는 경로는 `id` 열을 텍스트로 읽지 않고 `typeof(id)`와 `CAST(id AS BLOB)`로 읽으므로(`row_key`), UTF-8이 아닌 ID도 읽기를 실패시키지 않는다. 서버 시작은 건너뛴 행의 수와 ID만 표준 오류에 출력하고 질문 내용이나 로컬 경로는 출력하지 않는다. `save_question`(error 저장), `finish_question_cancel`, `end_unstored_question`도 질문을 끝난 상태로 저장할 때 같은 회차 변경을 함께 저장한다. 질문 취소(`POST /api/questions/{id}/cancel`, 정확히 `{expected_status}`)는 실행 취소처럼 확인창을 열 때의 상태와 저장된 상태가 같을 때만 대기 중인 질문을 바로 cancelled로, 처리 중인 질문을 cancelling으로 바꾼다. 저장된 상태가 cancelling이나 cancelled이면 `save_question`이 쓰기를 거부(RunCancelled)한다. 모델 호출 직전의 dispatched 호출 기록 저장도 거부되므로 취소가 커밋된 뒤에는 새 호출이 시작되지 않고, 그 뒤 저장할 차례가 온 답변도 저장되지 않는다. 작업자는 질문을 멈춘 뒤 cancelled로 기록한다. 결과 저장이 다른 오류로 실패할 때 쓰는 고정 문구 기록(`end_unstored_question`)도 취소된 질문에는 거부되므로 같은 cancelled 기록으로 이어진다. 그 기록 쓰기마저 모두 실패하면 cancelling으로 남고 재시작 때 cancelled로 복구된다(복구가 건너뛴 행은 제외). `Service.queue`는 등록된 실행·질문의 프로세스 메모리 목록이며 완료 순서를 보장하지 않는다. 목록 추가와 제출은 하나의 `queue_lock` 안에서 하고 끝나거나 취소된 항목은 지운다. 재시작으로 미완료 작업을 interrupted로 처리하므로 목록은 복원하지 않는다. 스케줄러는 작업 스레드를 시작한 뒤에만 작업을 큐에 넣는다. 따라서 스레드 시작 실패로 제출이 거부된 작업은 나중에 실행되지 않는다. 제출 실패 시 목록과 등록 상태를 정리하고 error 기록을 시도하며 슬롯을 한 번만 반환한다. 제출 래퍼가 작업을 넣은 뒤 오류를 던지는 경우에는 그 작업의 실행도 억제한다. 대기 중인 실행의 `queue.ahead`는 같은 단계에서 자리를 경쟁하는 작업이고, `queue.document_blockers`는 같은 문서의 호출·정리를 마치지 않은 이전 실행이다. 상태는 응답 시점의 DB 값이며, 다른 단계나 질문이 모두 끝나야 한다는 의미가 아니다. 대기 중인 질문의 `queue.ahead`는 질문 단계에서 앞선 질문뿐이고 질문에는 문서가 없으므로
