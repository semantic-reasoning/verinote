# verinote

원문을 등록하고, 개체·별칭·관계 사전을 먼저 승인하고, 그 사전으로 추출한 위키와 관계를 사람이 검토한 뒤, **실제 Wirelog로 승인된 지식만 조회**하는 로컬 웹 애플리케이션입니다. 문서 버전·정확한 인용·승인 이력·질의 스냅샷을 보존합니다. 여기서 xAI는 설명 가능한 AI(eXplainable AI)를 의미합니다.

## 실행

Python 3.11 이상이 필요합니다. 로컬 CLI를 쓰려면 해당 CLI의 설치·로그인이, OpenRouter API를 쓰려면 서버 키 파일과 모델 ID가 필요합니다.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
python -m verinote
```

브라우저에서 <http://localhost:8765>를 엽니다. 데이터 위치와 포트를 바꾸려면 `python -m verinote --data-dir /path/to/storage --port 8766`을 사용합니다. `verinote` 명령도 동일합니다. 프로그램은 `127.0.0.1`에만 바인딩됩니다.

웹의 **에이전트 설정 → Copilot 승인 사전 추출 · 파일당 청크 처리**에서 순차 1개 또는 병렬 최대 2개를 선택하고 **설정 저장**을 누릅니다. 재시작 없이 새 Copilot 추출부터 적용되며, 실행 중·대기 중인 작업은 등록 당시 설정을 유지합니다. 저장한 값은 재시작 후에도 유지되고 서버 시작 옵션보다 우선합니다.
저장한 설정이 없으면 `python -m verinote --copilot-extraction-concurrency 2`로 병렬 기본값을 지정할 수 있으며, 이 옵션도 없으면 순차 실행합니다. 파일 간 동시 실행 한도와는 별개입니다.
공유 상태·인증 갱신 충돌, 실제 동시 호출·요율·과금·`auto` 라우팅은 미확인이며,
실패 시 이미 시작한 호출의 비용이 더해질 수 있습니다. [계약·사용량·미확인 항목과 되돌리기](docs/extraction-concurrency.md#copilot-explicit-concurrency-2)를 확인하세요.

### 서버 전용 비밀 설정 파일

서버 자격 증명은 SQLite의 에이전트·모델·단가 설정과 별도로 TOML 파일에 보관합니다. 설정 화면에서 로컬 CLI 5종 또는 **OpenRouter (API)**를 선택해 사전·추출·인용 보정·질문을 실행합니다. API에는 실행 파일 설치가 필요하지 않습니다. 기본 위치는 다음과 같습니다. macOS에서 두 위치 모두 파일이 없으면 `--init-config`는 `~/Library/Application Support/verinote/config.toml`을 생성합니다. 우선 경로에 파일이 있으면 빈 키·형식·권한 오류가 있어도 다른 파일로 대체하지 않습니다.

| 환경 | 기본 경로 |
| --- | --- |
| macOS | `~/Library/Application Support/verinote/config.toml` 우선, 없으면 절대 경로인 `$XDG_CONFIG_HOME/verinote/config.toml` 또는 `~/.config/verinote/config.toml`의 기존 파일 |
| Linux/기타 POSIX | 절대 경로인 `XDG_CONFIG_HOME` 아래 `verinote/config.toml`, 없거나 상대 경로이면 `~/.config/verinote/config.toml` |
| Windows | `%APPDATA%/verinote/config.toml` (`APPDATA`가 없으면 `~/AppData/Roaming/verinote/config.toml`) |

POSIX에서 빈 파일을 안전하게 생성한 뒤 로컬 편집기로 `[openrouter]`의 `api_key`를 입력하세요. 실제 키를 명령 인자에 넣지 마세요.

```sh
python -m verinote --init-config
# 생성된 파일을 로컬 편집기로 편집한 뒤 서버 시작
python -m verinote
```

`--init-config`는 빈 `api_key = ""`를 쓰고 종료하며 서버·DB를 시작하지 않습니다. [config.example.toml](config.example.toml)은 비밀 없는 형식 예제입니다. 다른 위치를 사용하려면 생성과 실행 모두 `--config /absolute/path/config.toml`을 지정하세요. 명시적인 상대 경로는 실행 시 작업 디렉터리를 기준으로 해석합니다. 지정한 파일 하나만 읽으며 다른 파일이나 `OPENROUTER_API_KEY` 환경변수로 대체하지 않습니다.

파일은 최초 생성부터 `0600`, 앱이 새로 만드는 디렉터리는 `0700`으로 제한합니다. 생성 대상의 직접 부모는 현재 사용자 소유이며 그룹/다른 사용자 쓰기가 금지되어야 합니다. 기존 파일을 덮어쓰거나 기존 파일·디렉터리의 권한을 자동 수정하지 않습니다. 읽을 때도 현재 사용자 소유의 일반 파일과 정확한 `0600`을 요구하며 파일 자체의 심볼릭 링크·특수 파일은 거부합니다. 권한 오류가 있으면 소유자와 경로를 먼저 확인하고 `chmod 600 /absolute/path/config.toml`로 직접 복구하세요. 파일 크기는 64 KiB 이하이며 허용 항목은 `[openrouter].api_key` 문자열과 `[dictionary].relation_type_warning_threshold` 정수입니다.

기본 파일이 없거나 키 항목이 없거나 비어 있으면 미설정 상태로 기존 CLI를 사용할 수 있습니다. 명시한 파일 미존재·파싱/타입·읽기·권한 오류는 DB 복구 전에 서버 시작을 중단합니다. 파일은 서버 시작 시 한 번 읽으므로 편집 후 서버를 재시작하세요. 로더는 키를 환경변수나 DB에 쓰지 않으며 설정 여부만 공개할 수 있습니다.

**Windows의 파일 기반 비밀 설정은 이번 버전에서 지원하지 않습니다.** ACL을 검증하지 못하므로 `chmod` 결과를 보호의 증거로 사용하지 않습니다. 기본 파일이 없으면 CLI를 사용할 수 있지만, 기존 기본 파일·명시적 `--config`·`--init-config`는 안전한 오류로 거부합니다. 파일 기능이 필요하면 POSIX/WSL 환경을 사용하세요. Windows ACL 실제 검증은 수행하지 않았으며 지원을 주장하지 않습니다.

기본 위치는 저장소 밖이며 저장소 루트의 `config.toml`도 Git에서 제외합니다. 다른 이름으로 지정한 파일은 자동 제외되지 않으므로 실제 키 파일은 저장소 밖에 두세요. 파일은 평문이고 백업·같은 사용자·관리자 접근 및 추가 ACL에 대한 완전한 비밀 보호를 제공하지 않습니다. 파일 생성/읽기는 열린 디스크립터를 기준으로 검사하지만 악의적인 같은 사용자의 동시 내용 변경까지 막지는 않습니다.

## 사용 흐름

1. **문서 등록**: 파일을 선택하거나 텍스트를 붙여 넣습니다. TXT/MD/CSV/JSON/RST/LOG(UTF-8), 텍스트 PDF, DOCX를 지원합니다. 최대 원본 32 MiB, 추출 텍스트 128,000자, PDF 200쪽입니다. DOCX는 실제로 읽는 본문 XML(`word/document.xml`)의 압축 해제 크기가 16 MiB 이하여야 합니다. 이미지·첨부 파일은 압축을 풀지 않으며 이 본문 한도에 포함하지 않습니다. 다만 원본 32 MiB 제한에는 파일 전체가 포함됩니다. 원본 파일 크기와 본문 분석 한도는 별개이며 본문이 길면 문서를 나누어 등록하세요. OCR·암호화 PDF·이미지는 지원하지 않습니다. DOCX 본문 텍스트를 읽으며 페이지 배치·이미지·주석을 복원하지 않습니다.
2. **사전 생성 → 승인 → 추출**: 에이전트와 모델을 선택해 개체·별칭·관계 사전 초안을 생성합니다. 사전의 개체 ID·타입, 별칭의 동일성, 관계의 의미·방향·타입을 원문과 대조하고 필요하면 **내용 수정**의 JSON 편집기로 고친 뒤 승인합니다. 추출 점검에서 제외된 관계에 빠진 표기는 실행 기록의 **관계별 판단·사전 제약 보기**에서 **사전에 추가**로 별칭이나 새 개체로 넣을 수 있고, 타입이 맞지 않아 제외된 관계는 같은 곳의 **타입 고치기**로 관계의 허용 타입을 넓히거나 개체 타입을 바꿀 수 있습니다. 이어 **승인 사전으로 추출**을 누릅니다. 사전은 최대 4,000자 구간 64개, 관계 추출은 최대 8,000자 청크 16개를 처리하며 미완료 구간마다 선택한 CLI 또는 API를 호출합니다. 원문과 사전은 해당 모델 제공자에게 전달됩니다. 사전 승인 전에는 관계 추출을 시작할 수 없습니다. 위키와 관계는 다시 검토 대기로 저장됩니다.
3. **검토**: 각 위키 초안과 관계 사실을 원문과 대조하여 승인·보류·반려합니다. 여러 항목은 체크박스 또는 **검토 대기 전체 선택**으로 고른 뒤 **선택 N개 승인**을 누릅니다. 확인창에서 문서 버전·위키/관계 개수와 원문 근거를 확인하고 검토자·공통 승인 이유를 한 번 입력합니다. 위키 승인과 관계 승인은 별개이며 각 항목에 승인 이력이 남습니다. 관계를 수정하면 새 후보 revision이 생기고 다시 검토해야 합니다. 기존 승인 철회도 가능합니다.
4. **자연어 질문**: 관계 탐색 화면에서 질문과 에이전트·모델을 선택합니다. LLM이 고정 도구를 선택하고 실제 Wirelog 결과를 받은 뒤 인용이 연결된 답변을 생성합니다. 질문 이력·실행 추적·원문 버전·JSON 다운로드를 제공합니다. **고급 관계 탐색**: 직접 관계 또는 특정 관계의 도달 대상·역방향 출발점·경로를 조회합니다. 예를 들어 `주문 / depends_on / 원장`을 경로 조회하면 실제 PyreWire 결과와 사실 ID 경로, 원문 인용을 표시합니다. 문장 생성과 관계 조회는 구분됩니다.
5. **새 문서 버전**: 문서 상세의 `새 버전 등록`으로 같은 문서의 다음 버전을 추가합니다. 버전 선택·원본 다운로드·이전 버전 텍스트 diff를 제공합니다. 새 버전 등록 즉시 최신 버전이 현재 기준이 되며, 이전 버전의 승인 사실은 현재 그래프에서 제외됩니다. 새 버전은 다시 추출·검토합니다. 새 버전 등록만으로 과거 원문과 판정이 삭제되지는 않습니다. 다만 이 문서의 사전 재생성이나, 병렬 수나 청크 임계 정책을 등록한 관계 추출이 대기·처리 중이면 새 버전 등록을 거부합니다. 이 실행들은 요청된 때부터 끝날 때까지 원문 버전 등록이나 삭제가 없어야 결과를 저장하기 때문입니다.
6. **재현**: 질의 결과 JSON을 다운로드하거나 최근 질의에서 과거 스냅샷을 재조회합니다. 당시 승인 사실의 내용과 문서 버전을 보존하므로 이후 수정·철회와 분리하여 탐색할 수 있습니다.

승인 사전으로 추출할 때 **모든 관계 종류를 하나씩 점검**하고 기술 구성·운영 관계와 나열된 항목을 검토합니다. 특허·설계의 직접 서술은 승인 관계 정의가 그 설계 의미를 보존할 때만 관계 후보로 추출합니다. 조건·부정·선택적 동작을 무조건적 사실로 바꾸지 않습니다. 실행 기록의 **관계별 판단·사전 제약 보기**에서 관계별 추출 개수, 직접 근거 없음, 표현 제약, 사전의 개체·관계·타입 부족과 해당 위키 주장 번호를 확인하세요. 주장 번호는 그 실행의 위키에 대응하며 기존 결과와 실행 ID로 구분합니다.

새 추출 응답에서 `extracted`로 표시한 관계에 실제 같은 관계의 사실이 있으면, `fact_indices`의 누락이나 다른 관계 사실을 가리키는 참조를 추가 모델 호출 없이 보정합니다. 올바른 기존 참조는 순서를 유지하고, 다른 관계 참조를 제거한 뒤 누락된 같은 관계 인덱스를 추가합니다. 사전 불일치로 제외된 사실이 없는 새 응답은 실제 배열 범위를 넘은 인덱스도 보정하되, 참조 배열은 최대 80개, 값은 0~80의 중복 없는 정수로 제한합니다. 행 안의 중복·정수가 아닌 값·음수·80을 넘는 값은 거부합니다. 사전 불일치 제외가 있으면 범위 밖 참조는 계속 거부하며, 상태나 사실·인용은 바꾸지 않습니다. 이는 점검표의 참조 보정이며, 사실의 정확성이나 추출의 완전성을 보장하지 않습니다. 새 응답의 설명 참조(`claim_indices`)에 존재하지 않는 번호가 섞인 경우, 유효한 참조가 하나 이상 남을 때만 없는 번호를 제거합니다. 점검 행과 사전 제약 항목에 적용하며, 실제 설명·사실·인용이나 유효한 참조는 보존합니다. 참조는 최대 12개, 값은 0~12의 중복 없는 정수여야 하며 모두 잘못된 참조라면 중단합니다. 의도한 연결을 추측하거나 남은 참조의 의미적 타당성을 보장하지 않습니다. 실행 상세에는 이번 실행의 보정 건수를, `runs/<실행>/<청크>/coverage-repair.json`에는 변경 전후와 응답 해시를 기록합니다. 설명 참조를 제거한 감사 기록은 schema 2로 대상 배열·행·필드를 명시하고, 사실 인덱스만 보정한 기존 schema 1은 유지합니다. 변경 전 해시는 제외를 적용하기 전 파싱한 응답의 해시이고, 변경 후 해시와 인덱스는 아래 사전 불일치 제외를 적용한 뒤의 응답과 번호를 기준으로 하며, 그 뒤 근거 불가 제외가 있으면 최종 번호와 달라질 수 있습니다. 기록 저장에 실패하면 해당 청크는 확정하지 않습니다. 이전 청크 재사용은 유지하며 재사용한 보정은 이번 실행 건수에 다시 넣지 않습니다. 이전 기록이나 재사용 연결이 없으면 과거 보정 여부를 알 수 없습니다.

새 추출 응답의 관계가 승인 사전과 일치하지 않으면(승인된 개체·별칭 중 표기가 정확히 일치하는 것이 없는 참조, 승인 관계의 방향/타입 불일치) 그 관계만 저장에서 제외하고 나머지를 처리합니다. 제외 자체는 모델을 호출하지 않으며, 남은 관계나 위키 주장의 인용 보정은 아래 규칙대로 호출할 수 있습니다. 승인 사전에 없는 관계 ID나 주어·관계·목적어의 형식 오류는 제외하지 않고 실패 처리합니다. 이런 관계가 하나라도 있으면 그 응답에서는 일치하지 않는 관계도 제외하지 않고 청크를 중단하며, 실행 상세는 제목·위키 주장·사실 개수 오류는 사실보다 먼저 검사하므로 그 오류를 표시하고, 그런 오류가 없으면 일치하지 않는 관계를 건너뛰어 사실 중 응답 순서로 처음 걸리는 중단 원인의 번호와 사유를 표시합니다. 제외를 마친 뒤 남은 관계의 인용 오류로 중단하면 번호가 제외 뒤 기준임을 함께 표시합니다. 제외한 관계의 인용은 검증하지 않으므로 인용 형식이 잘못되어도 실패하지 않습니다. 제외한 관계가 있으면 성공한 실행은 상세 앞부분(아래 근거 불가 제외가 있으면 그 다음)에 응답 관계 수 중 제외 수와 되살리는 방법을 표시하고, 실패한 실행도 상세에 검증을 마친 청크의 제외 수를 표시합니다(상세는 2,000자에서 잘리므로 오류 문구가 길면 빠질 수 있습니다). 점검 보고서를 사용할 수 있으면 **관계별 판단·사전 제약 보기**에 표기 그대로의 주어·목적어와 관계 ID(앞뒤 공백만 정리), 이유, 최대 300자 인용을 표시합니다. 이 인용은 원문과 대조하지 않은 모델 작성 문구이며 문자열이 아니면 `없음`으로 표시합니다. 각 행에는 문제가 있는 주어·목적어마다 개체 ID·별칭에 없는 표기인지(개체 이름과 정확히 같으면 그 사실과 ID를 표시하고, ID는 앞의 5개까지만 보여 주며 나머지는 개수로 표시합니다) 타입이 맞지 않는지와 허용 타입을 함께 표시하고, 제외 사유(개체 ID·별칭에 없는 표기, 타입 불일치)별 수를 나눠 보여 줍니다. 한 행에 두 문제가 함께 있으면 표기 쪽으로 셉니다. 타입 불일치는 별칭이나 새 개체를 추가해도 해결되지 않습니다. 현재 문서 버전의 실행이라면 개체 타입을 바꾸거나 관계의 허용 타입을 넓혀 다시 승인한 뒤 재추출하면 저장될 수 있지만, 재추출은 모든 청크를 새로 호출하고 보충 점검 호출이 더 있을 수 있으며 되살아난다는 보장은 없습니다. 타입이 맞지 않는 주어·목적어에는 표기 문제와 함께 있는 행에서도 **타입 고치기** 버튼이 붙으며, 나타나는 조건은 아래 **사전에 추가**와 같습니다. 대화상자는 미리 고르지 않은 두 방법 중 하나를 직접 고르게 합니다. 관계의 그 자리 허용 타입에 그 개체의 현재 타입을 넣거나, 개체 타입을 그 관계의 그 자리 허용 타입 중 하나로 바꿉니다. 타입은 정확한 문자열로만 비교하며, 공백이나 보이지 않는 문자만 다른 허용 타입이 있으면 알리기만 합니다. 어느 쪽이든 그 한 곳만 바꾸고 사전은 새 revision의 검토 대기가 됩니다. 넓히면 그 타입의 개체가 모두 그 자리에 허용되고, 타입을 바꾸면 그 개체를 쓰는 다른 관계가 재추출에서 새로 제외될 수 있으며, 대화상자는 현재 사전, 이 실행의 점검 보고서와 이 문서 버전의 관계 후보로 센 영향과 재추출 비용 안내를 보여 줍니다. 점검 보고서로 세는 통과 수는 실행 당시 사전 revision이 현재와 같을 때만 셉니다. 서버는 그 자리 허용 타입 밖의 타입으로 바꾸는 것과, 그 타입의 마지막 개체인데 그 타입을 허용하는 관계가 있을 때의 타입 바꾸기를 거부합니다. 보충 점검 응답에서 걸린 미해결 후보에는 이 버튼이 없고 영향 수에도 들어가지 않습니다. 개체 ID·별칭에 없는 표기에는 **사전에 추가** 버튼이 붙습니다. 실행이 끝났고, 그 실행이 현재 문서 버전의 것이며, 그 버전의 사전이 반려되지 않았을 때만 나타납니다. 대화상자에서는 별칭(대상 개체를 직접 고름) 또는 새 개체를 고르고, 원문에 그대로 나오는 구간 중에서 인용을 고릅니다. 대상 검색은 현재 사전에서 입력한 글자가 ID나 이름에 그대로 들어간 개체만 찾으며, 표기와 이름이 정확히 같은 개체(현재 사전의 전부)를 먼저 보여 줄 뿐 대신 고르지 않고 공백을 지운 비교도 쓰지 않습니다. 타입 경고도 현재 사전의 관계 허용 타입 기준입니다. 추가하면 사전은 새 revision의 검토 대기가 되므로 승인과 재추출은 따로 해야 하고, 재추출은 모든 청크를 새로 호출하고 관계가 0개로 끝난 구간이 있으면 보충 점검 호출이 최대 4회 더 있을 수 있으며, 제외된 관계가 되살아난다는 보장은 없습니다. 대화상자는 이 비용과 한계를 함께 보여 주며, 예상 비용에는 인용 보정과 보충 점검이 빠집니다. 이 문서 버전의 실행이 대기·처리 중이면 저장이 거부되고, 추가를 되돌리는 버튼은 없습니다. 이 판정은 실행에 고정된 사전 revision 기준으로 보기 때마다 계산하며 파일에 저장하지 않습니다. 현재 사전 revision이 다르거나 문서 버전이 바뀌었으면 그 사실을 함께 표시합니다. 어떤 관계의 사실이 모두 제외되면 그 점검 행은 로컬에서 `not_representable`로 바뀝니다.

일부만 제외되고 다른 실패가 없는 실행은 성공이므로 같은 사전 revision·추출 방식으로 다시 추출할 수 없습니다. 제외된 관계를 되살리려면 사전을 수정·재승인한 뒤 재추출하며, 이때 모든 청크를 다시 호출합니다. 실행 전체에 남은 응답 관계가 없고 이처럼 사전과 일치하지 않아 제외한 관계가 하나라도 있으면 위키 주장과 후보를 저장하지 않고 실패로 끝나며 같은 revision으로 다시 추출할 수 있습니다. 이 실행과 추출 조건이 같은 재실행이 모든 청크의 호환되는 복구 기록을 찾으면 검증된 청크를 재사용해 새 호출 없이 같은 실패로 끝납니다. 사전을 수정·재승인하면 모든 청크를 새로 호출합니다. 다른 모델로 바꿀 수도 있지만 그 모델의 호환되는 복구 기록을 찾으면 검증된 청크를 재사용하므로 같은 실패로 끝날 수 있습니다. 이 제외는 사전 불일치만 다루며, 보정 뒤에도 인용을 확인하지 못한 항목의 제외는 아래 인용 보정 규칙을 따릅니다. 점검 행 수 오류 같은 다른 검증 실패나 호출 실패는 그대로 실행을 실패시킵니다.


이 점검은 **모델 자체 판단**입니다(제외로 바뀐 행은 로컬 처리). 보고서가 일관되어도 누락이 없거나 의미가 정확하다는 보장은 없으며, 최소 사실 수를 강제하지 않습니다. 필수 점검 항목이 잘못되면 인용이 정확한 응답도 저장 전에 실패할 수 있습니다. 다른 오류가 먼저 걸리지 않은 채 점검 행 수가 승인 관계 수와 맞지 않으면 실행 상세가 승인 관계 수·응답 행 수·승인되지 않은 행 수·중복 관계 수·행이 없는 관계(최대 5개)를 그대로 알리지만(해당하는 항목만), 그 응답은 후보로 저장하지 않으며 다시 추출하면 재사용할 복구 기록이 없는 청크를 새 모델 호출로 요청하고 같은 결과가 나올 수 있습니다. 별도 누락 보충 호출은 추가하지 않지만 보고서 출력 토큰은 사용량에 포함됩니다. 사전의 반복 인용을 프롬프트에서 제외해 중복 입력을 줄이며 저장된 승인 사전과 검증 기준은 유지합니다.

이전 방식으로 추출한 문서는 같은 승인 사전에서 **개선된 방식으로 다시 추출**을 한 번 사용할 수 있습니다. 같은 사전 revision·현재 방식의 성공 실행은 반복하지 못하며 실패는 재시도할 수 있습니다. 이전 승인·보류·거절 이력은 보존되고 새 결과는 검토 대기로 추가되므로 중복 관계가 생길 수 있습니다. 사전 자체에 필요한 관계 정의가 없으면 사전을 수정·재승인해야 합니다. 보고서 파일 저장 실패는 검증된 결과의 저장을 취소하지 않으며, 보고서 미확인을 누락 0개로 표시하지 않습니다.

업로드 창의 진행 막대는 **파일 준비 → 서버 전송 → 서버 문서 처리 → 원문 등록 완료**를 구분합니다. 전송률은 원본 파일 크기가 아니라 base64를 포함한 실제 HTTP 요청 바이트 기준입니다. 전송 100% 뒤에도 본문 추출·저장이 남아 있으므로 서버의 등록 완료 응답 전에는 처리 중으로 표시합니다. 전송 중에는 입력·중복 등록·창 닫기를 잠그고, 실패하면 입력을 다시 사용할 수 있습니다. 연결 중단이나 응답 시간 초과 시에는 서버가 이미 저장했을 수 있으므로 문서 목록을 확인한 뒤 재시도하세요.

문서 상세와 실행 기록에서 **사전 생성 및 위키·관계 추출 진행 막대**를 볼 수 있습니다. 검증을 마친 글자 수와 구간 수를 표시하며, 사전 재시도에서는 재사용한 검증 구간도 포함합니다. 모델이 응답하는 동안에는 다음 구간이 검증될 때까지 수치가 그대로입니다. 모든 구간 검증 후에도 저장 중에는 최대 99%이며 DB 저장 성공 후 100%가 됩니다. 실패·중단·취소는 해당 상태로 표시하며, 취소한 실행의 진행률은 100%가 되지 않습니다(모든 구간을 검증한 뒤 취소하면 99%일 수 있습니다). 진행 기록이 없거나 손상됐으면 비율을 추측하지 않습니다. 대기 중인 실행에는 같은 단계에서 앞서 처리 중이거나 기다리는 실행을 처리 순서대로 최대 5개까지 현재 상태와 함께 표시하고 나머지는 개수로 알려 줍니다. 대기 중인 질문에는 앞서 처리 중이거나 기다리는 질문을 같은 방식으로 표시합니다. 질문은 별도 작업자에서 처리하므로 실행을 기다리지 않습니다. 페이지를 새로고침한 뒤 문서나 실행 기록을 열면 진행 중인 작업 조회가 이어집니다. 진행률은 예상 남은 시간이나 크레딧을 뜻하지 않습니다.

## 에이전트와 모델

| UI 이름 | 실행 방식 | 모델 선택 |
| --- | --- | --- |
| Claude | 상시 `claude -p --input-format stream-json --output-format stream-json` 프로세스 재사용, 요청마다 대화 초기화 | `--model ID` |
| Antigravity | `agy --output-format json --mode plan --sandbox --disable-slash-commands -p PROMPT` | `--model ID` |
| GitHub Copilot | `copilot --silent --usage-output-file PATH --available-tools '' --disable-builtin-mcps -p PROMPT` (Windows에서는 prompt를 stdin으로 전달) | `--model ID` |
| Cursor | `cursor-agent --output-format stream-json --mode ask --sandbox enabled --trust -p PROMPT` | `--model ID` |
| Codex | `codex exec --json --skip-git-repo-check --ephemeral --sandbox read-only --color never -` | `--model ID`, prompt는 stdin |

Cursor는 `cursor-agent`가 없으면 `agent` 실행 파일을 탐색합니다. 설정 화면에서 기본 에이전트와 **각 에이전트별 모델 ID**를 저장하고, 추출 직전에 해당 작업의 모델을 바꿀 수도 있습니다. 모델 목록을 하드코딩하지 않으며 빈 값은 CLI 기본 모델을 뜻합니다. 모델 가용성·로그인은 CLI 계정에 따릅니다. 설치 여부만으로 모델 접근 가능성을 보장하지 않습니다.

Windows의 Copilot은 서버 프로세스의 `PATH`를 먼저 탐색하고, 찾지 못하면 WinGet의 `%LOCALAPPDATA%\Microsoft\WinGet\Links`와 npm의 `%APPDATA%\npm`도 확인합니다. 터미널에서 실행되더라도 서버가 설치 전의 `PATH`를 상속했다면 기존 PATH 탐색만으로는 미설치로 표시될 수 있습니다. 다른 경로에 설치했다면 해당 경로를 `PATH`에 추가한 터미널에서 서버를 다시 시작하세요.

CLI는 별도 작업 폴더에서 실행하며 shell 문자열을 사용하지 않습니다. 권한 우회 옵션은 사용하지 않습니다. 기본 실행 제한은 **사전 생성은 모든 에이전트에서 호출당 600초(10분)**, **승인 사전 기반 위키·관계 추출은 모든 CLI/API에서 청크당 최대 360초(6분)**입니다. 인용 보정 호출도 해당 청크의 남은 360초 예산을 공유합니다. 자연어 질문은 Antigravity(`agy`)와 GitHub Copilot 600초, 나머지 180초입니다. 코드에서 지정한 `CLI(timeout=...)`는 사전 생성·질문에 우선 적용하며, 추출에서는 더 짧은 제한만 적용합니다. 전체 작업은 여러 청크로 더 오래 걸릴 수 있습니다. 시간 초과나 검증 실패에 대한 자동 유료 재호출은 없습니다. 적용된 제한은 실행 로그의 `timeout_seconds`와 시간 초과 메시지에서 확인할 수 있습니다. stdout+stderr 제한은 1 MiB이며 오류·시간 초과는 실패로 기록합니다. 대기·실행 중 작업은 질문을 포함해 최대 8개입니다. 사전 생성은 서로 다른 파일 2개, 승인 사전 기반 위키·관계 추출도 서로 다른 파일 2개를 동시에 실행하므로 문서 작업은 총 4개까지 진행합니다. 질문은 별도 작업자 1개에서 순차 처리합니다. 같은 파일의 실행은 단계를 가로질러 겹치지 않으며, 취소 중인 이전 호출과 자원 정리가 끝나야 재실행합니다. 대기 화면의 같은 단계 작업 목록은 경쟁 중인 작업이며 모두 끝나야 한다는 뜻은 아닙니다. 서버 재시작 시 미완료 작업은 중단 상태로 바뀌고, 취소 중이던 실행과 질문은 취소됨으로 바뀝니다. 실행 폴더 격리가 OS 수준의 완전한 격리를 뜻하지 않으며 각 CLI 자체 권한 정책도 적용됩니다.

추출은 검증 완료된 청크 결과를 `data/runs/<run-id>/extraction-checkpoint.json`에 저장합니다. 실패·서버 중단·취소 후 **같은 문서 버전·승인 사전 revision·에이전트·모델로 승인 사전 추출을 다시 실행**하면 저장된 완료 청크를 재검증해 재사용하고 그다음 청크부터 호출합니다. 병렬 수·청크 임계 정책을 등록한 실행에서 뒤 청크가 실패하면, 실패 전에 이미 허용한 앞 청크 호출의 응답은 청크 제한 시간 안에서 기다려 검증하고 실패 뒤 새 호출 없이 통과하면 저장합니다. 실패 뒤에 새로 인용 보정 호출이 필요해진 앞 청크나 검증에 실패한 앞 청크는 저장하지 않으므로 다시 실행하면 그 청크부터 호출합니다. 앞 청크가 실패하면 이미 끝난 뒤 청크의 응답도 저장하지 않고 다시 호출합니다. 예외로, 남은 청크의 전체 요청이 입력 예산을 넘어 호출 전에 거부된 실행은 같은 문서 버전·승인 사전·에이전트로 다시 실행해도 같은 크기로 거부되므로 실행 상세의 다음 단계가 필요합니다. OpenRouter의 토큰 상한·어댑터 계약과 소스·프롬프트·추출 방식도 일치해야 합니다. 시간 제한만 바뀐 경우에는 기본 실행에서 완료 청크를 재사용합니다. 병렬 수나 청크 임계 정책을 등록한 Claude 실행은 worker가 1개여도 병렬 설정, 시간 제한, 실행 파일 경로, 출력 한도, 단가, 문서 세대까지 일치해야 하며, 다르면 그 기록을 재사용하지 않습니다. 병렬 수나 청크 임계 정책을 등록한 실행과 등록하지 않은 실행도 서로의 기록을 재사용하지 않습니다. 같은 문서·에이전트·모델의 최근 실패·중단·취소 실행 8개의 기록만 살펴봅니다. 대기 중에 취소한 실행은 모델을 호출하지 않았으므로 이 8개에 세지 않습니다. 청크 처리 단계에서 실패한 실행의 상세는 저장된 청크 수를 기준으로 같은 조건의 재시도가 호출할 청크를 표시하며, 실패 시점의 상태이므로 그 뒤 다른 실행이 추출을 완료하면 재시도가 거부될 수 있습니다. 남은 청크가 호출 전에 크기로 거부된 실패, 저장할 내용 없음, 실행 중 문서·사전 등이 바뀌어 끝난 실패에는 이 문구가 없습니다. 복구 기록이 없거나 손상·비호환이면 다시 처리하며 실행 상세에 이유를 표시합니다. 저장 실패도 상세에 표시하므로 이전 청크를 반드시 재사용한다고 보장하지는 않습니다. 재사용 청크에는 모델을 다시 호출하지 않으며, 전체 추출이 성공해야만 위키·관계 후보를 한 번에 저장합니다. 후보의 별도 검토·승인 절차는 유지합니다.

원문 인용은 PDF 추출에서 생길 수 있는 `U+0001` 같은 비NUL 제어문자도 내부 그대로 보존하며, 저장 원문과 정확히 일치해야 합니다. 인용의 앞뒤 공백 정리는 기존과 같고, 정리 전 8,000자 한도·NUL 금지·빈 인용 금지는 유지합니다. 이름·ID·정의·설명 등 모델이 작성하는 일반 필드의 제어문자 제한은 완화하지 않습니다. 기존 문서의 원문·해시를 바꾸거나 다시 업로드할 필요는 없습니다.

관계 추출 결과의 인용이 원문에 없으면, 먼저 승인 사전과 일치하지 않는 관계를 제외하고 남은 응답의 형식과 승인 사전의 개체·관계·타입을 검사합니다. 제외한 관계의 인용은 보정하지 않습니다. 다른 문제가 없으면 계약 v2의 제품 추출은 먼저, 원문에 없는 인용과 공백 런(스페이스·탭·줄바꿈)의 폭만 다른 구간을 찾습니다. 그런 구간이 원문에 정확히 한 곳이면 모델 호출 없이 인용을 그 원문 구간으로 바꿉니다. 띄어쓰기는 한국어 의미를 바꿀 수 있으므로 공백을 지우거나 더해서 맞추지 않으며, 맞는 위치가 여럿이거나 그중 하나라도 원문 런에 줄바꿈이 2개 이상이면 바꾸지 않습니다. 확정한 구간에는 모델이 인용한 내용만 있고 모델 보정이 고를 수 있었던 더 넓은 문맥은 없으므로, 검토자는 그 구간이 해당 주장이나 관계를 뒷받침하는지 확인해야 합니다. 남은 문제 인용이 있을 때만 같은 에이전트·모델에 **문제가 있는 인용문만 다시 선택**하도록 요청합니다. 원문에 없는 단어를 임의로 지우거나 유사한 문장을 자동 인정하지 않습니다. 보정은 청크당 한 번이고 실행당 상한은 없습니다. 모든 청크가 보정을 요구하면 호출 수는 청크 수의 두 배(최대 16청크에서 32회)까지 늘고 그만큼 시간과 크레딧이 더 듭니다. 재개한 실행은 재사용하지 못한 청크만 호출합니다. 사전 생성과 자연어 질문에는 이 위치 확정과 보정을 적용하지 않습니다.

보정은 주장 내용·관계 triple·정상 인용을 유지하고, 해당 청크의 정확한 연속 원문 인용만 허용합니다. 보정 응답은 행 단위로 판정합니다. 통과한 행은 인용을 교체하고, 보정 뒤에도 인용이 원문의 한 위치로 확인되지 않은 행(빈 문자열 응답 포함)은 그 위키 주장이나 관계만 저장하지 않고 나머지를 처리합니다. 보정을 요청하지 않은 행은 제외하지 않습니다. 응답 형식 오류(경로 누락·중복·추가 필드, 문자열이 아닌 인용), 시간 초과, 호출 실패는 제외로 바꾸지 않고 실행을 실패 처리하며 청크와 주장/관계 번호(사전 불일치 제외 후 번호)를 표시합니다. 성공하면 이번 실행의 보정 건수와 위치(제외 뒤 남은 항목 기준 번호)를 실행 기록 및 완료 알림에 표시하고 결과는 **검토 대기**로 저장합니다. 정확한 문구 일치는 의미가 맞다는 보증이 아니므로 보정되거나 위치를 확정한 인용도 사람이 대조해야 합니다. 최초 응답 로그는 유지하며 `data/runs/<run-id>/<chunk>/quote-repair/`에 보정 호출 로그와 변경 전후 `changes.json`, 제외한 행이 있으면 경로와 최대 300자의 이전 인용·응답을 담은 `refused.json`을 남깁니다. 두 기록의 저장에 실패하면 해당 청크는 확정하지 않습니다. 보정 요청이나 `refused.json`에 들어갈 문구에 UTF-8로 인코딩할 수 없는 문자(짝 없는 서로게이트)가 있으면 그 행을 제외하지 않고 실행을 실패 처리합니다.

위치를 확정한 인용은 보정 건수에 합산하지 않고, 실행 상세에 확정 건수와 위치(청크와 제외 뒤 남은 항목 기준 번호)를 따로 표시합니다. 호출 없이 확정만 있어도 성공 상세에 원문 대조 안내가 나옵니다. 이 건수는 이번 실행에서 검증을 마친 청크만 셉니다. 실패 실행은 앞서 검증을 마친 청크의 건수를 표시하고, 재개 실행은 재사용 청크의 확정을 세거나 위치를 표시하지 않으며, 성공 상세에는 그 청크에 대해 일반 대조 안내와 이전 실행 ID만 나옵니다. 행마다 변경 전후 인용은 `data/runs/<run-id>/<chunk>/quote-located.json`에 남습니다. 이 파일은 보정 호출 전에 쓰므로 파일이 있다고 그 청크가 저장된 것은 아니며, 번호는 이후 근거 불가 제외가 반영되지 않은 사전 불일치 제외 후 번호입니다. 이 기록의 저장에 실패하면 해당 청크는 확정하지 않습니다.

이렇게 제외한 항목이 있는 성공 실행은 상세 맨 앞에 제외 건수와 청크·번호(보정을 요청한 응답 기준)를 사전 불일치 건수와 분리해 표시합니다. 이 성공으로 같은 사전 revision·추출 방식의 재추출은 막히며, 제외 항목만 복구하는 기능은 없습니다. 사전을 수정·재승인해 재추출하면 모든 청크를 새로 호출하고 같은 결과가 나올 수 있습니다. 제외한 위키 주장은 저장 위키와 후보에 넣지 않으며, 점검 보고서를 사용할 수 있으면 최대 300자의 본문·인용과 함께 **관계별 판단·사전 제약 보기**에 표시합니다. 이 문구는 근거로 쓰지 않습니다. 남은 주장과 관계의 근거 번호는 다시 매깁니다. 제외한 주장만 근거였던 표현 제약 행은 근거 번호 없이 로컬 사유로 남고, 제외한 주장만 가리키던 사전 제약은 그 기록으로 옮겨 사전 제약 수에서 뺍니다.

한 청크의 주장이 모두 제외되면 재호출 없이 주장 0개 청크로 확정하고 그 청크의 관계는 유지합니다. 실행 전체에 남은 주장이 없으면 게시하지 않고 실패로 끝나며 revision을 소비하지 않습니다. 이 실행과 추출 조건이 같은 재실행이 모든 청크의 호환되는 복구 기록을 찾으면 새 호출 없이 같은 결과로 끝납니다. 사전을 수정·재승인하거나 다른 모델을 선택하면 호환되는 복구 기록을 찾지 못한 청크는 새로 호출합니다. 주장은 남고 모든 관계가 인용을 확인하지 못해 제외된 실행은 주장만 게시하고 제외를 상세에 표시합니다.

벤치마크와 진단 실행은 사전 등록한 계약대로 문서당 보정 한도와 전부 실패 동작을 유지하므로 공백 런 위치 확정을 적용하지 않고 이 제외 경로에 도달하지 않습니다. 그 결과를 제외 동작의 근거로 쓰지 마세요.

CLI 옵션은 설치된 도움말과 [Claude 공식 CLI 문서](https://docs.anthropic.com/en/docs/claude-code/cli-usage), [Cursor CLI 문서](https://cursor.com/docs/cli/overview), [Copilot 도구 제한 문서](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools)를 기준으로 확인했습니다. CLI 버전이 달라 옵션 오류가 발생하면 실행 로그를 확인하세요.

## 사용량과 크레딧

로컬 CLI 5종과 OpenRouter API가 보고한 토큰을 자동 저장합니다. **실행 기록**에서 에이전트·모델·사전 생성/관계 추출/인용 보정/누락 보충 점검/질문/질문 분할 분석/질문 이진 종합/질문 최종 결정/기존 추출별 합계와 JSON 다운로드를, 개별 실행·질문에서 호출별 사용량과 계산 근거를 확인합니다. 실패·취소한 작업의 호출, 재시도, 질문의 여러 LLM 호출도 포함합니다. 요청을 보내기 전에 실패했다는 근거가 남고 그 호출의 사용량 기록(usage.json)을 받아들일 수 있는 호출은 시작하지 않은 호출로 따로 표시하고 확인된 호출과 사용량 합계에서 제외합니다. 확인된 호출은 시작하지 않은 호출과 호출 횟수 미확인 작업을 뺀 호출로, 시작한 호출과 기록으로는 시작 여부를 가릴 수 없는 호출(usage.json을 받아들일 수 없는 호출 포함)을 셉니다. 시작하지 않은 호출의 근거는 제공자마다 다릅니다. 로컬 CLI는 CLI 프로세스를 띄우지 못한 경우(실행 파일 없음, OS가 프로세스 시작을 거부함 등), 지속 연결 Claude는 이 호출을 위해 CLI 프로세스를 띄우지 않았고 기존 worker도 받지 못한 경우(실행 파일 없음, OS가 프로세스 시작을 거부함, 잠금·pool 대기 시간 초과 등), OpenRouter는 HTTP 요청의 첫 바이트를 보내기 전에 실패한 경우(DNS·연결·TLS 단계 실패 포함), Ollama는 생성 요청 전에 실패한 경우(서버 미실행·모델 미설치 등)입니다. 생성 요청 여부 기록(`generate_requested`)이 없는 예전 Ollama 호출은 이 근거가 없어 요청 전 실패도 확인된 호출로 남습니다. 요청을 보낸 뒤의 실패는 지금처럼 확인된 호출로 셉니다. usage.json이 없거나 읽을 수 없거나 (OpenRouter·Ollama에서) run.json의 호출 기록과 맞지 않아 받아들일 수 없는 호출은 run.json에 이 근거가 있어도 확인된 호출로 셉니다. 취소 중인 실행에서 아직 끝나지 않은 호출은 종료 경고 없이 진행 중으로 표시하고, 그 호출의 사용량은 호출이 끝날 때 기록됩니다. 대기 중에 취소한 실행과 질문은 모델을 호출하지 않았으므로 호출 0회로 표시합니다. 처리 중에 첫 모델 호출 전에 실패하거나 취소된 사전 생성·관계 추출 실행도 실행이 끝날 때 저장한 진행 기록의 새 호출 시도 수가 0이면 호출 0회로 표시합니다. 실행 상세의 새 호출 시도 수는 시작하지 않은 호출도 셉니다. 그 기록이 없거나 실행이 끝날 때 저장되지 못했으면 호출 횟수를 확인할 수 없다고 표시합니다. 처리 중에 첫 모델 호출 전에 실패하거나 취소된 질문과, 서버 재시작으로 중단된 질문도 저장된 호출 계획 목록이 비어 있거나 계획(planned)만 담고 있으면 호출 0회로 표시합니다. 질문은 모델을 호출하기 직전에 그 호출의 dispatched 상태를 호출 계획 목록에 저장하고, 이 저장이 실패하면 호출하지 않습니다. 실패·취소·중단으로 끝난 질문에서 호출 계획 목록에 dispatched나 failed로 남은 항목에 읽을 수 있는 호출 로그(run.json·usage.json)가 하나도 없으면, 그 호출이 시작됐는지 기록으로 알 수 없으므로 그 항목은 확인된 호출로 세지 않고 호출 횟수를 확인할 수 없다고 표시합니다. 각 파일은 경로에 symlink가 없고 256 KiB 이하이며 서버가 열어 읽을 수 있는 파일이면 내용이 비어 있거나 손상되어도 읽을 수 있는 로그로 보며, 그런 로그가 하나라도 있는 항목은 호출로 세며, 그 호출의 usage.json을 받아들일 수 있고 위의 시작하지 않은 근거가 남아 있으면 확인된 호출이 아니라 시작하지 않은 호출로 셉니다. 그 호출의 사용량은 usage.json에서 읽고(OpenRouter와 Ollama는 run.json의 호출 기록과도 맞아야 합니다), usage.json이 없거나 해석할 수 없거나 맞지 않으면 그 호출의 사용량을 미확인으로 표시합니다. 로컬 CLI와 Ollama는 첫 호출 로그를 쓰지 못하면 요청하지 않지만 OpenRouter는 그래도 요청을 보내고, 쓴 로그도 나중에 지워지거나 읽을 수 없게 될 수 있으므로, 어느 제공자든 0회로 표시하지 않습니다. 호출 로그를 쓰기 전에 실패한 질문 호출(모델 ID 검사 등)은 기록이 없으므로 위 규칙대로 호출 횟수를 확인할 수 없다고 표시합니다. 이 목록이 없는 예전 질문은 호출 로그가 없으면 호출 횟수를 확인할 수 없다고 표시합니다(대기 중에 취소한 질문은 호출 0회). 승인과 고급 관계 탐색 자체는 LLM을 호출하지 않습니다.

| --- | --- |
| 입력·출력 토큰 | CLI 또는 API envelope가 보고한 카운터. 입력에는 캐시, 출력에는 추론이 포함되어 세부 값을 다시 더하지 않습니다. |

**설정 → 사용량 계산 단가**에서 에이전트별 추정을 켜고 일반 입력·출력·캐시 읽기·캐시 쓰기 단가를 모두 입력합니다. 크레딧으로도 보려면 계약상의 단위 이름과 크레딧 1개당 USD를 지정합니다. 단가는 자동으로 추측하지 않습니다. 모델 ID를 지정하면 제공자가 보고한 실제 모델과 우선 대조하고, 보고가 없을 때만 요청 모델을 가정으로 사용합니다. 단가 모델을 비우면 모델을 지정하지 않은 호출에만 ‘CLI 기본 모델 가정’으로 적용합니다. 여러 모델을 합산한 호출이나 모델 불일치는 추정하지 않습니다.

단가와 환산 기준은 **각 호출 시작 시 고정**됩니다. 설정을 바꿔도 과거 비용은 재계산하지 않습니다. 보고 비용과 추정 비용을 서로 더하지 않으며 크레딧은 단위별로 구분합니다. 구독 한도, 할인, 실제 청구액·잔액은 별도입니다.

집계는 **보존된 최근 1,000개 실행·질문 작업**의 읽을 수 있는 호출 로그를 대상으로 하며 전체 작업 수와 누락 범위를 표시합니다. 오래된 기록, 손상·누락된 로그, 제공자가 보내지 않은 값은 **미확인**이지 0이나 무료가 아닙니다. 이미 끝난 과거 호출은 원문 글자 수로 토큰을 추측하거나 로그를 재작성하지 않습니다. 일부 카운터만 있으면 확인된 값의 소계와 기록 수를 표시합니다. 문서 삭제로 연결된 실행·질문이 제거되면 해당 사용량도 집계에서 빠지므로 평생 누적 지출이 아닙니다.

사용량은 `data/runs/{id}/{구간}/usage.json`(사전 1~64, 관계 추출 1~16), 인용 보정은 그 아래 `quote-repair/usage.json`(제외 기록은 같은 폴더의 `refused.json`), 관계 추출의 누락 보충 점검은 같은 구간 폴더의 `recovery/usage.json`, 질문은 `data/questions/{id}/llm-{회차}/usage.json`, 분할 처리 호출은 같은 질문 폴더의 `context-{회차}-{번호}/usage.json`(분석·이진 종합)과 `context-{회차}-decision/usage.json`(최종 결정)에 저장합니다. 원본 CLI 출력과 별도로 저장하며 Copilot 전용 파일과 정규화된 사용량 파일의 읽기 한도는 각각 256 KiB입니다. CLI 응답 형식이 달라지면 사용량이 미확인이 되거나 명시적인 실행 오류가 발생할 수 있습니다.

## 결정성과 설명 가능성의 경계

- LLM 추출 자체는 비결정적입니다. **같은 승인 사실 스냅샷 + 같은 규칙 + 같은 PyreWire 버전 + 같은 질의**에서 정렬된 관계 결과와 선택된 증명 경로가 같습니다.
- 모든 관계는 일반 triple입니다. 전이는 사용자가 지정한 동일 predicate 내에서만 계산합니다. 관계 이름이 같다는 이유로 인과관계·장애 발생·시간적 유효성을 보장하지 않습니다. 필요하면 의미가 다른 관계는 후보 검토 시 이름을 분리하세요.
- 증명 경로는 정렬된 승인 사실에서 결정적으로 고른 최단 경로 하나입니다. 엔진 내부 provenance 전체를 출력하는 기능은 아닙니다. 직접 관계에는 이를 지지하는 모든 승인 사실 ID가 표시됩니다.
- 정확한 인용의 존재는 의미의 정확성을 증명하지 않습니다. 조건·부정·시점이 손실된 관계는 승인하지 않아야 합니다. 시스템은 사람의 판정을 대신하지 않습니다.
- 자연어 질의 해석과 답변 문장은 비결정적입니다. 실제 도구 호출·결과·인용을 기록합니다. 인용 ID와 근거 유형 검증은 의미적 정답 보증이 아닙니다. 승인 그래프·승인 위키·미검토 원문·추론을 구분합니다. 빈 결과는 현실의 부재를 뜻하지 않습니다. 임베딩 검색과 사용자 정의 Datalog 실행은 제공하지 않습니다.

## 질문의 지식 조회 순서

여러 문서를 결합하는 질문에는 대상과 방법론 양쪽의 승인 지식을 검색·읽도록 안내합니다. 빈 직접 관계만으로 자료 부재를 단정하지 않으며, 사실과 근거에 기반한 제안을 구분하도록 요청합니다. 이 안내와 답변 보정이 모델의 탐색 완전성이나 전략의 타당성을 보장하지는 않습니다.

질문은 **승인된 위키와 관계 그래프를 우선 사용**합니다. 승인 사전의 개체·별칭·관계 정의는 어휘 안내로 검색되며, 그 자체를 관계 사실의 근거로 인용하지 않습니다. 그래프만으로 답할 수 있으면 위키·원문 읽기를 추가하지 않습니다. 문서 설명은 승인 위키를 찾아 읽고 `승인 위키` 근거로 답합니다.

원문 본문 검색·읽기는 해당 문서의 승인 지식 검색과 그래프 조회 결과를 받은 뒤에만 가능합니다. 관련 위키가 검색되면 먼저 읽고, 다음 모델 회차에서 부족한 내용을 구체적으로 설명해야 합니다. 실행 기록과 원문 근거에 검색 ID·이유·읽은 위키 근거 ID가 남습니다. 승인 위키 없음, 관련 위키 검색 결과 없음, 읽은 위키의 설명 부족, 과거 스냅샷에 위키 정보 없음을 구분합니다. 이 검사는 조회 순서·문서 범위를 확인하며 모델의 검색어 선택이나 의미적 부족 판단의 정확성을 보장하지 않습니다. 원문 내용은 계속 `미검토 원문`으로 표시합니다.

위키 읽기는 원문 인용을 포함한 페이지 내용을 2,000자씩 제공하며 부분 구간·주장 번호·다음 위치를 표시합니다. 승인 지식 검색은 20개씩 제공하며 잘린 검색 결과로 원문 접근을 허용하지 않습니다. 검색어·문서 범위를 좁혀야 합니다. 제목·파일명 검색은 원문을 읽지 않습니다. 논리 회차는 최대 6회, 도구는 최대 10회이며 예산이 부족하면 실패하거나 확인 범위를 한정해 답합니다. 자연어 질문은 문서 100개·사실 500개·위키 500개·사전 100개, 승인 위키·사전 합계 8 MiB까지입니다. 개별 도구 결과의 기존 30,000바이트 제한은 제거했으며 원본 결과를 보존합니다. 매 호출의 전체 프롬프트는 앱 정책상 60,000바이트까지입니다. 연결 도구가 더 낮은 입력 예산을 제공하면 그 값을 적용합니다. 이 바이트 예산은 모델의 토큰 한도가 아닙니다. 특히 Copilot `auto`처럼 호출 전 실제 모델·시스템 지시문·출력 예약량을 확정할 수 없는 경로는 모델 토큰 한도를 미확인으로 기록하며, 과거 사용량이나 모델 카탈로그의 최대 컨텍스트를 안전한 입력 한도로 간주하지 않습니다.

전체 요청이 입력 예산을 넘으면 **현재 요청의 모든 기록을 자동으로 분할 분석하고 종합**합니다. E 근거, 검색 결과를 포함한 각 도구 추적 기록, 카탈로그 항목을 원본 해시와 함께 배정합니다. 하나의 기록도 입력 예산을 넘으면 JSON 경로별 조각으로 나누며, 긴 문자열은 정확한 문자 위치를 붙여 분할합니다. 각 조각의 원본 ID·해시·순번·전체 조각 수를 보존하고 모든 조각의 처리 응답을 확인한 뒤 종합합니다. 조각은 독립적인 승인 근거가 아니며, 빠진 문맥이나 전체 그래프의 부재를 단정할 수 없습니다. 크기를 맞추려고 기록을 버리거나 인용문·그래프 증명의 내용을 생략하지 않습니다. 저장된 원본 근거와 실행 추적은 그대로 유지합니다. 모든 묶음에 원래 질문과 회차 지시를 전달하며, 모델이 배정된 기록마다 발견 또는 관련 발견 없음의 이유를 반환해야 다음 단계로 진행합니다. 이는 지금까지 조회된 기록의 처리이며 아직 조회하지 않은 문서 전체를 읽었다는 뜻이 아닙니다.

각 묶음의 분석은 **미승인 모델 해석**입니다. 두 하위 분석을 함께 입력하는 이진 종합을 반복하고, 모든 하위 ID가 처리되었는지 검사합니다. 분석 응답 바이트 한도는 원래 질문·두 분석·지시문을 담는 실제 직렬화 예산에서 계산합니다. 묶음을 정할 때 입력 크기와 함께 기록별 출력 공간(구조·ID·인용과 텍스트 512바이트 여유)을 고려합니다. 그래도 최초 분석 응답이 종합 입력용 한도를 넘으면, 최대 1 MiB 안에서 전체 형식·기록 ID·인용을 먼저 검증하고 기록을 통째로 로컬 분할해 종합합니다. 원래 응답과 분할 출처를 보존하며 분석 재호출이나 문자열 잘라내기는 하지 않습니다. 기록 하나조차 한도에 들어가지 않거나, 종합 응답이 한도를 넘거나, 기록/하위 ID·인용이 잘못되면 계속 실패합니다. 최종 답변은 전달된 분석 ID를 인용하는 `inference`만 허용하며 분석 아래에서 원본 E와 해시를 추적합니다. 모델 해석이 원본 승인 사실로 승격되거나 원문 접근을 허용하지 않습니다. 직접 전체 원본을 전달한 일반 답변의 검증 규칙은 유지합니다.

탐색·답변은 최대 6개 **논리 회차**입니다. 한 회차가 B개 입력 묶음이고 분석 응답을 L개 로컬 묶음으로 나누면 분석 B회 + 이진 종합 L−1회 + 최종 결정 1회, **B+L회 물리 호출**이 필요합니다. 로컬 묶음은 입력 기록·조각 수 N을 넘지 않으므로 시작 전에 최대 B+N회를 확보합니다. 회차당 기록·조각 상한은 2,048개이며 전체 물리 호출 상한은 `2 × 6 × 2048 = 24,576`입니다. 최초 분석 호출 계획을 실행 전에 저장하고, 로컬 분할 결과로 정해진 각 종합 호출도 전송 전에 저장하며 암묵적인 분석 재시도는 하지 않습니다. 동일 질문·스냅샷·모델·입력·회차 지시·출력 한도·분할 규칙이 정확히 일치하는 검증 결과만 재사용합니다. 추가 호출은 시간과 비용을 증가시키며, 실패한 호출까지 사용량에 집계합니다.

`context_processing`에 계획/처리한 기록·조각 및 묶음 수, 전체 원본 해시 목록, 조각 경로·내용·범위, 분석 트리와 상태를 남기며 `analysis_nodes`에 중간 분석과 출처, `analysis_leaf_responses`에 검증된 최초 분석 응답과 해시를 보존합니다. 로컬 분할은 제공자 호출로 세지 않으며, 답변 인용 검증 시 원래 응답과 각 조각의 정확한 내용·중복 없는 전체 포함 관계를 다시 검사합니다. 화면의 처리 수는 **전달 및 응답 범위 검증**이지 의미적 완전성이나 모델의 정확한 이해를 보장하지 않습니다. 어느 묶음이라도 실패하면 완료된 종합 답변으로 표시하지 않습니다. 필수 질문·지시·최소 조각조차 입력 예산에 들어가지 않거나 한 회차의 기록·조각이 2,048개를 넘으면 분할 호출 전에 실패하며, 알 수 없는 제공자 토큰 한도·통신 오류까지 제거하지는 못합니다. 기존 전체 확장 상태 8 MiB·200,000노드·깊이 96 제한은 유지합니다. `context_budget`은 각 실제 요청의 바이트 크기와 앱/어댑터 한도 출처, 모델 토큰 한도 미확인을 기록합니다.

6회 중 **탐색은 최대 5회이며 마지막 1회는 답변 전용**입니다. 도구 10회를 먼저 사용하면 바로 다음 모델 호출을 답변 전용으로 전환합니다. 마지막 탐색 결과를 전달하고 이미 읽은 근거로 답하며, 부족하거나 읽지 못한 부분은 확인 불가로 한정하도록 요청합니다. 답변 전용 회차의 추가 도구 요청은 실행하지 않습니다. 최종 answer의 로컬 검증(형식·인용)이 실패하면 남은 회차 안에서 한 번만 답변 보정을 요청합니다. 거절된 초안과 검증 이유를 전달하고 이미 읽은 근거만으로 다시 답하게 하며 추가 도구는 허용하지 않습니다. 보정도 논리 회차 6회 한도와 입력 크기 한도를 소비하고 시간·비용이 들 수 있습니다. 보정 실패나 마지막 회차의 오류는 그대로 실패하며 7번째 논리 회차를 추가하지 않습니다. 통신·인증·응답 파싱·도구 실행 오류는 이 보정 대상이 아닙니다.

긴 검색어로 승인 지식을 찾지 못하면 그 문장에 포함된 문서명·파일명(확장자 제외)·승인 사전 개체·별칭으로 후보를 찾습니다. 문서명은 한국어 띄어쓰기 차이도 허용하며, 별칭은 해당 문서 사전의 정규 명칭으로만 확장합니다. 한 글자나 일반적인 이름은 이 보조 검색에서 제외합니다. 위키 후보를 사전 안내보다 먼저 표시하고, 검색 결과에 `match_mode`와 `matched_terms`를 남깁니다. 보조 검색의 후보 이름이 12개를 넘으면 불완전한 검색으로 표시하므로 문서 범위·검색어를 좁혀야 합니다. 후보 검색은 원문이나 인용문을 검색하지 않으며 그 자체를 답변 근거로 인용할 수 없습니다.

같은 질문에서 성공한 그래프 조회를 반복하면 기존 결과와 근거 ID를 재사용합니다. 실행 추적의 `reused_from`은 처음 성공한 도구 요청 번호(1부터 시작)를 가리키며, 반복 요청도 10회 한도에 포함됩니다. Copilot의 빈 `<final_answer>` 접두 태그, Cursor·Copilot의 정확히 동일한 JSON 객체 2회 반복은 추가 모델 호출 없이 정리합니다. 처리 내역은 호출 로그 `run.json`의 `response_normalizations`에 남으며 원본 출력과 사용량은 보존합니다. 서로 다른 응답이 섞이거나 알려지지 않은 형식이면 계속 실패합니다.

새 스냅샷은 승인 위키·사전·관계와 문서 메타데이터를 함께 고정합니다. 이후 승인 철회·새 버전 등록은 과거 질문의 근거를 바꾸지 않습니다. 기존 스냅샷은 재작성하지 않으며, 위키 정보가 없으면 현재 위키를 가져오지 않고 명시적인 원문 fallback을 사용합니다. 위키와 관계의 승인은 여전히 별개이며, 검토 대기·보류·반려 위키는 질문 근거에 포함하지 않습니다.

새 질문과 그래프는 문서·원문 버전·고정 사전별 개체/관계 참조를 사용해 동명 개체를 자동으로 합치지 않습니다. 질문 화면은 가능한 의미와 각 출처·승인 상태·연결된 승인 사실을 모델 답변과 별도로 표시합니다. 모호한 전이/경로 조회는 참조 선택이 필요하며, 과거 스냅샷은 기존 계산을 유지합니다. [의미 후보와 식별 계약](docs/entity-ambiguity.md)에 선택 방법과 한계를 정리했습니다.

## 저장과 운영 범위

기본 `data/verinote.sqlite3`에 원본 바이트·추출 텍스트·SHA-256·문서 버전·초안·사실·검토 이벤트·설정·스냅샷·질의 기록이 저장됩니다. `data/runs/<run-id>/<chunk>/`에는 CLI의 실제 prompt, stdout, stderr, 실행 메타데이터가 저장됩니다. API 호출은 stdout을 만들지 않고 안전 검사한 `response.json`, `run.json`, `usage.json`을 별도 보관합니다. 일반 API·다운로드에는 원시 HTTP 응답이나 Authorization 헤더를 포함하지 않습니다. SQLite 실행 기록에는 단계와 추출에 사용한 승인 사전의 ID·revision·내용·SHA-256도 고정하여 보존합니다. 이 폴더는 Git에서 제외합니다. 백업할 때 서버를 종료한 뒤 데이터 폴더 전체를 복사하세요.

단일 사용자 로컬 애플리케이션입니다. 검토자 이름은 사용자가 입력하는 감사 기록이며 인증된 신원이 아닙니다. 인터넷 공개·다중 사용자 권한 관리·데이터 암호화를 제공하지 않습니다. 같은 데이터 디렉터리에 서버를 여러 개 실행하지 마세요. HTTP 서버는 로컬 Origin/Host 검사와 JSON 요청 제한을 사용합니다. UI는 원문·모델 출력을 HTML로 실행하지 않습니다.

일괄 승인은 **현재 보고 있는 한 문서 버전의 검토 대기 위키·관계 중 선택한 항목**에만 적용합니다. 사전은 별도로 승인하며 보류·반려·이미 승인된 항목은 개별 검토합니다. 한 번에 최대 2,000개를 처리하고, 전체 선택이 한도를 넘으면 일부를 해제해야 합니다. 확인창을 연 뒤 새로 생성된 항목은 자동으로 포함되지 않습니다. 선택한 항목이나 문서가 변경되면 전체 요청을 취소하고 새로 선택하도록 안내합니다. 부분 승인과 자동 재시도는 하지 않습니다. 과거 버전도 명시적으로 검토할 수 있지만 현재 그래프에는 현재 버전의 승인 사실만 들어갑니다. 승인은 모델을 호출하지 않으므로 AI 크레딧을 사용하지 않습니다.

## 검증

```sh
python -m unittest discover -s tests -v
node --check verinote/web/app.js
```

테스트는 실제 PyreWire 엔진으로 승인/미승인, 경로, 사이클, 관계 혼합 방지, 철회 및 스냅샷 재현을 확인합니다. 문서 버전·동시 승인·추출 중 새 버전·잘못된 인용·실패/타임아웃·HTTP 신뢰 경계도 검사합니다. 외부 CLI는 테스트 transport와 실제 연동 검증을 구분합니다.

설계와 참고 자료 학습 내용은 [architecture](docs/architecture.md), [learning notes](docs/learning-notes.md)에 있습니다.

자연어 질문은 제출 시 스냅샷과 에이전트·모델을 고정합니다. 최대 문서 100개/승인 사실 500개, 논리 회차 6회(분할 분석 물리 호출 별도), 도구 10회(회당 3개), 원문 읽기 2,000자, UTF-8 프롬프트 60,000바이트를 허용합니다. 개별 결과는 30,000바이트를 넘더라도 보존하고 필요하면 분할합니다. 누적 입력 초과는 모든 기록을 분할 분석·종합하며, 최소 요청조차 담을 수 없는 한도 초과·보정 후에도 잘못된 인용·실행 오류는 실패로 남깁니다. 질문 로그는 `data/questions/<id>/llm-<round>/` 또는 `context-<round>-<node>/`, 답변과 도구 추적은 SQLite에 보존합니다. 질문 이력은 저장 답변을 열고, 다시 질문은 별도 실행을 생성합니다. 답변을 만들었지만 저장하지 못했고 오류 상태는 저장할 수 있으면, 질문은 답변 없이 오류 `답변을 만들었지만 저장하지 못했습니다.`로 저장됩니다.

## 원문 삭제

문서 상세에서 **최신 리비전 vN만 삭제**와 **문서 전체 삭제**를 구분합니다. 과거 버전을 보고 있어도 최신 삭제의 대상은 표시된 현재 최신 vN입니다. 확인창에서 삭제 범위를 확인한 뒤 실행합니다.

- 최신 리비전만 삭제하면 남은 가장 최신 리비전과 그 위키·승인 사실이 현재 기준으로 돌아옵니다. 리비전이 하나뿐이면 전체 삭제를 사용합니다.
- 문서 전체 삭제는 문서 및 모든 리비전의 원문·위키·사실·검토 이력·추출 기록을 제거합니다.
- 삭제한 버전을 포함한 스냅샷과 그 스냅샷의 모든 질문·답변·조회 이력도 제거합니다. 여러 문서를 함께 조회한 이력도 포함됩니다. 영향받지 않은 과거 스냅샷은 유지합니다.
- 삭제한 버전 번호는 재사용하지 않습니다. 예를 들어 v2 삭제 후 v1로 돌아가도 다음 등록은 v3입니다. 버전 비교는 가장 가까운 남은 이전 버전을 사용합니다.
- 추출·질문 작업이 대기/실행 중이면 삭제를 거부합니다. 작업 완료 후 다시 선택하세요. 처리 중인 실행이나 질문을 취소했다면 실행 기록이나 질문 이력에서 `취소됨`으로 바뀐 뒤 삭제하세요. `취소 중`인 동안에도 삭제를 거부하며, 이미 허용한 호출이 끝나면 `취소됨`이 됩니다(추출 청크는 최대 360초, 사전 생성 호출은 기본 600초, 질문 호출은 위의 자연어 질문 제한 시간). 그 시간이 지나도 바뀌지 않으면 서버를 재시작하세요. 대기·실행 중인 추출이나 사전 재생성은 같은 문서 버전의 사전 검토도 거부합니다. 오래된 화면의 변경 요청도 충돌로 거부하며 자동 재시도하지 않습니다. 사전 재생성이나, 병렬 수나 청크 임계 정책을 등록한 관계 추출이 대기·처리 중이면 그 문서의 새 버전 등록도 거부합니다.
- 관련 로컬 CLI 로그도 정리합니다. 파일 삭제 실패 시 DB 삭제는 유지하고 **로그 정리 대기**를 표시합니다. 실행 기록의 재시도 버튼이나 서버 재시작으로 남은 작업을 재시도합니다.

삭제는 되돌릴 수 없습니다. 이미 다운로드한 파일, 별도 백업, 모델 제공자 측 기록을 회수하거나 디스크의 물리적 완전 소거를 보장하는 기능은 아닙니다. 기존 API 클라이언트는 다음 버전 등록 및 삭제 시 문서 GET 응답의 `current_version`, `generation`을 각각 `expected_version`, `expected_generation`으로 보내야 합니다.

## 문서 이름으로 질문하기

“등록한 문서가 무엇인가?”처럼 제목을 묻는 질문에는 승인 위키를 먼저 읽고 **승인 위키** 근거로 설명합니다. 승인 그래프가 비어 있어도 위키 설명은 가능합니다. 승인 자료로 답할 수 없을 때만 조회 이력과 부족한 이유를 검증한 뒤 원문을 읽으며, **미검토 원문** 근거로 표시합니다. 문서 제목의 일반적 정의나 법률적 효력까지 자료에 없는데 보충하지는 않습니다. 일반 정의가 필요하면 그 정의를 설명하는 참고 문서를 함께 등록하세요.

문서 검색은 기본적으로 제목·파일명만 NFC/casefold로 비교합니다. 본문 검색은 특정 문서에 대한 원문 보충 조건을 통과한 경우에만 허용합니다. 검색 결과는 문서를 찾는 용도이며 인용 근거가 아닙니다. 모델은 승인 위키 또는 허용된 원문을 실제로 읽어 인용합니다. 읽기 범위와 남은 분량을 전달하여 부분 읽기를 문서 전체 확인으로 혼동하지 않도록 합니다. 정규화 전용 본문 일치의 읽기 시작점은 0이며 정확한 일치 위치를 뜻하지 않습니다. 긴 문서는 도구·문맥 한도 안에서 추가 읽기가 필요할 수 있습니다. 같은 제목의 문서는 파일명·버전으로 구분해 질문하면 좋습니다.


## 추출 사전과 품질

`llmwiki-demos/llmwiki-wirelog`는 미리 준비한 개체·별칭·관계 사전과 승인 스냅샷으로 질의하는 데모입니다. 실행 중 임의 문서를 같은 수준으로 추출하는 비교 기준은 아닙니다. 기존 verinote는 짧은 자유 형식 프롬프트로 관계를 생성해 `calls`/`depends_on`, `managed_by`/`owned_by`처럼 어휘가 달라지고, 명시된 서비스 ID 대신 여러 표기를 사용했습니다. 원문 인용의 존재만 검사하므로 이 차이를 걸러내지 못했습니다.

이제 문서 버전별 사전을 사람이 먼저 승인합니다. 정규 개체 ID와 승인된 별칭의 정확한 표기만 허용하고, 관계 ID 및 주어·목적어 타입을 검사합니다. 사전에 없는 관계를 자동으로 추가하지 않습니다. 예를 들어 내부 서비스의 직접 호출을 `depends_on: Service → Service`, 운영 책임을 `owned_by: Service → Team`으로 정의하면 문서 담당을 서비스 소유 관계로 저장할 수 없습니다. 띄어쓰기는 뜻을 바꿀 수 있으므로 사전 생성에서 모델이 제안한 별칭은 대상 개체의 ID·이름이나 같은 개체의 다른 별칭과 공백(스페이스·탭·줄바꿈, 런 폭 차이 포함)만 다르면 연결하지 않고 제외하며, 제외 사유가 이를 밝힙니다. 별칭이 대상 개체의 이름과 정확히 같으면 유지하지만, 그 이름이 대상의 ID와 공백만 다르면 제외합니다. 사전 생성, 검토 화면과 **타입 고치기**에서 공백을 뺀 비교는 거부와 표시에만 쓰고 표기를 찾거나 제안하거나 연결하는 데는 쓰지 않습니다(질문의 문서 제목 보조 검색은 개체·별칭·사실을 연결하지 않고 읽을 문서만 고르므로 이 규칙의 범위 밖이며, 공백을 뺀 비교로 제목을 맞춥니다. [#887](https://github.com/semantic-reasoning/verinote/issues/887)). 이 보호는 모델이 제안한 별칭과 `revisions`에 적용됩니다. `revisions`로 개체 이름을 그 개체 ID와 띄어쓰기만 다른 표기로 바꾸는 제안은 묶음 전체를 보류하며, 같은 대상이라고 판단하면 사람이 **내용 수정**으로 이름을 바꿉니다. 이 이름 변경 보류와 검토 화면 표시에서 띄어쓰기만 다르다는 것은 공백을 빼면 같고 한쪽에만 공백이 있는 자리가 있다는 뜻입니다. 별칭 제외와 달리, 한쪽에 줄바꿈이 있는 자리는 원문 줄바꿈이 띄어쓰기를 지웠을 수 있어 띄어쓰기 차이로 보지 않고, 공백 폭이나 종류만 다른 자리도 띄어쓰기 차이로 보지 않습니다. 남은 한계는 다음과 같습니다. 모델이 만든 개체 행의 ID와 원문 명칭이 띄어쓰기만 다르면 그 행을 거부하지 않고 저장하므로, 조회와 질문 안내가 두 표기 모두로 그 개체를 찾습니다. 이런 개체는 검토 카드와 검토 창에 표시하지만 승인을 막지 않습니다. 통합되어 사라진 개체의 이름은 사전의 ID·이름·별칭에 남지 않으므로(통합 별칭의 인용에는 남습니다), 그 이름과 공백만 다른 표기가 이후 청크에서 별칭이나 통합으로 같은 대상에 들어오면 막지 못합니다([#884](https://github.com/semantic-reasoning/verinote/issues/884)). 추출은 승인된 ID·별칭과 정확히 같은 표기만 받지만 사실의 주어·목적어 표기가 인용에 있는지는 검사하지 않으므로, 추출 모델이 원문의 다른 띄어쓰기를 보고 승인된 ID를 쓰면 그 사실은 그 ID로 저장 후보가 됩니다. 사실을 승인할 때 인용과 주어·목적어를 대조하세요([#885](https://github.com/semantic-reasoning/verinote/issues/885)). 새 추출 응답에서 승인된 표기와 (앞뒤 공백을 정리한 뒤) 정확히 맞지 않는 표기를 쓴 관계는 제외하고 저장하지 않습니다. 이 보호와 검토 화면 표시는 공백이 아닌 문자(길이가 없는 문자, 빈칸처럼 보이는 한글 채움 문자 U+3164)를 공백으로 보지 않고, 유니코드 정규화 형식이 다른 표기는 다른 문자로 비교합니다. 그래서 이런 문자가 한쪽에만 있거나 자리가 달라 공백을 빼도 두 표기가 같지 않으면, 눈에 보이는 띄어쓰기가 달라도 모델 별칭과 `revisions` 이름 변경을 거부하지 않고 ID·이름 목록에도 표시하지 않습니다([#886](https://github.com/semantic-reasoning/verinote/issues/886)). **타입 고치기**의 허용 타입 알림은 기준이 달라, 길이가 없는 서식 문자(유니코드 Cf)도 빼고 비교하며 한글 채움 문자는 빼지 않습니다. 사람이 같은 대상이라고 판단하면 별칭을 추가할 수 있으며 형태가 두 가지입니다. 하나는 그 표기와 개체 명칭을 모두 포함하는 연속된 원문 인용(8,000자 이하)을 가진 별칭입니다. 다른 하나는 별칭 행에 `judged_alias`·`judged_entity`·`judged_name` 세 키를 두어 사람이 판단한 표기·대상·대상 이름을 고정한 별칭이며, 이 별칭의 인용에는 별칭 표기가 있어야 하지만 개체 명칭은 없어도 됩니다. 이 세 키가 있는 행은 대상 개체의 이름을 바꾸거나, 별칭을 다른 개체로 옮기거나, 별칭 표기를 고치면 사전 검증에서 거부되므로 사람이 다시 판단해 키를 갱신해야 합니다. 이 키는 생성·추출 프롬프트와 질문 안내에 넣지 않습니다(인용 보정 프롬프트는 사전을 평범한 JSON으로 보낼 때 예외로 세 키를 함께 보내며, 큰 사전을 표 형태로 바꿔 보낼 때는 빠집니다. 검토자 이름과 이유는 어느 쪽에도 보내지 않습니다). 한 인용에 두 표기가 함께 있다고 같은 대상임이 증명되지는 않으며, 두 형태 모두 같은 대상이라는 사람의 판단입니다. **사전에 추가**는 인용에 개체 명칭이 없을 때 세 키를 기록하고, 승인 화면은 이런 별칭을 앞에 모아 두 원문 인용·고정한 이름·판단한 검토자와 이유를 보여 줍니다. **내용 수정**의 JSON 편집기로 사전을 고치면 새 revision이 되어 다시 승인해야 하고, 그 뒤 추출은 모든 청크를 새로 호출합니다. 별칭을 추가해도 관계의 방향/타입 검사는 그대로이므로 타입이 맞지 않는 관계는 저장되지 않습니다. 두 끝점의 타입이 같은 관계의 방향 오류나 인용의 의미까지 자동 증명하지는 않으므로 사람의 검토가 필요합니다.

- 사전 생성의 **구간별 응답**은 개체 200개, 별칭 400개, 관계 40개까지입니다. 문서 전체 누적 사전은 최대 64개 구간을 기준으로 개체 12,800개, 별칭 25,600개, 관계 2,560개까지 보존하며, 검증된 인용을 포함해 UTF-8 24 MiB까지입니다. 개수와 바이트 제한을 모두 만족해야 합니다. 인용은 사전 항목마다 반복될 수 있어 전체 저장 한도와 별도로, 저장된 정의에 60,000바이트 제한을 적용하지 않습니다. 설정 화면의 **사전 표 전환 기준**(기본 60,000, 1~120,000 UTF-8 바이트)은 정의를 평범한 JSON으로 보낼지 표로 보낼지 고르는 기준이며, 이 값만으로 실행을 거부하지 않습니다. 개체는 `id/name/type/quote`, 별칭은 `alias/entity/quote`, 관계는 `id/description/subject_types/object_types/quote`로 편집합니다. `name`은 인용에 있어야 하고 별칭 인용에는 해당 별칭과 개체 `name`이 함께 있어야 합니다. 관계 설명에는 의미·포함·제외 기준을 적습니다.
- 개체 ID에는 `order` 같은 공식 ID나 문서 간에도 의미 있는 정규 명칭을 사용하세요. `e1` 같은 임의 번호는 피하고, 서로 다른 FSM의 같은 상태명은 `주체 FSM:활성 상태`처럼 구분하세요. 그래프는 ID 문자열로 연결하므로 문서 간 동일 ID의 다른 의미·동일 개체의 다른 ID는 사람이 맞춰야 합니다. 전역 사전 병합 기능은 제공하지 않습니다.
- **사전 표 전환 기준**은 설정 화면에서 바꾸며 SQLite에 저장됩니다. 모델별 토큰 한도에서 산출된 수치가 아니라 앱 정책의 사용자 설정입니다. 60,000은 과거 전체 사전 한도에서 계승한 기본값입니다. 작업 등록 시 값을 고정하므로 변경은 이후 새 작업부터 적용됩니다. `/api/settings` PUT의 선택적 정수 `dictionary_context_bytes`로도 설정할 수 있으며 기존 클라이언트가 생략하면 저장값을 유지합니다.
- 평범한 JSON 표현이 설정한 기준이나 전체 요청 예산을 넘으면 모든 정의를 **무손실 행·문자열 표**로 변환해 전송하고, 표도 설정한 기준을 넘거나 표가 전체 요청 예산에 들어가지 않으면, 전체 요청 예산에 들어가는 더 작은 쪽 형식(표 요청이 더 크면 평범한 JSON)을 그대로 전송합니다. 설정한 기준을 넘는다는 이유로 실행을 거부하지 않습니다. 개체·별칭·관계·타입·설명·순서는 그대로 복원하며 정의 해시를 검증합니다. 요약·생략·추가 모델 호출은 하지 않습니다. 누적 정의가 60,000바이트를 넘어도 기존 저장 한도 내에서 검증·저장하고 다음 구간을 계속 처리합니다. 승인 사전 추출과 인용 보정에도 같은 전송 방식을 적용합니다. 작은 인용 보정 요청은 기존 전체 pin 표현을 유지하며, 변환할 때는 중복 사전 인용만 제외하고 모든 정의·승인 pin 식별자·문제 인용·원문을 유지합니다.
- 전체 요청은 지시문·원문·표 해석 규칙을 모두 포함해 기존 120,000바이트와 연결 도구의 더 작은 예산을 지켜야 합니다. 정의 외 내용까지 무제한으로 보낼 수 있는 것은 아닙니다. 평범한 JSON과 표 형식이 모두 전체 요청 예산을 넘으면 검증된 진행을 보존하고 실제 전체 요청 크기와 입력 예산을 표시하며 거부합니다. 이 경우 표 전환 기준을 바꿔도 해결되지 않습니다. 120,000바이트는 앱 정책이며 제공자 한도로 확인된 값이 아닙니다. 거부 상세에는 그 상태에서 가능한 다음 단계만 비용과 함께 표시합니다. 다른 에이전트로 처음부터 실행하는 단계는 Ollama가 아닌 다른 제공자의 CLI가 설치되어 있거나 API 키가 구성되어 있고(로그인·모델 접근 권한은 확인하지 않습니다) 요청이 120,000바이트 이내일 때만, 완성된 사전을 줄여 재승인하는 단계는 전송 정의에서 줄일 수 있는 바이트로 초과분을 덮을 수 있을 때만 표시합니다. 사전 생성 거부는 통과한 앞부분이 있으면 그 크기를, 없으면 더 작은 크기를 기준으로 문서를 나누도록 안내하며, 사용자가 생성 중인 정의를 직접 줄이라는 요구는 하지 않습니다. 이 안내를 따라도 사전 생성의 뒤 구간이나 더 조밀한 부분에서 다시 거부될 수 있으며 그 전 호출 비용은 발생합니다. 승인 사전 추출은 첫 호출 전에 남은 청크를 모두 같은 예산으로 검사해, 넘는 청크가 있으면 모델을 호출하지 않고 가장 많이 넘는 청크를 표시합니다. 인용 보정 요청은 문제 인용에 따라 커지므로 이 검사로 미리 알 수 없어 청크 호출 뒤에 거부될 수 있습니다. 사전 생성이 끝나도 추출은 완성된 사전 전체를 보내므로 별도로 거부될 수 있습니다. 그래서 사전 생성이 성공하면 모델을 호출하지 않고, 그 사전을 수정 없이 승인해 생성과 같은 에이전트로 추출할 때의 첫 호출 전 검사를 미리 계산합니다. 거부되는 경우에만 실행 상세 앞부분에 경고를 표시하며(문서 화면은 아래처럼 다시 계산합니다), 기준으로 삼은 에이전트와 입력 예산, 다음 단계를 함께 보여 주고 승인이나 추출을 막지 않습니다. 승인 전에는 승인될 revision의 자릿수를 알 수 없으므로 요청 크기는 하한(이상)으로, 줄일 바이트는 근사값으로 표시합니다. 요청이 120,000바이트를 넘으면 다른 에이전트로도 거부된다고, 넘지 않으면 다른 에이전트로는 거부되지 않을 수 있다고 표시합니다. 문서 화면은 현재 문서 버전의 반려되지 않은 사전에 대해, 화면을 불러올 때마다 모델을 호출하지 않고 현재 사전과 현재 추출 프롬프트·계약 버전·입력 예산·요청 구성으로 그 사전을 생성한 실행의 에이전트 기준 첫 호출 전 검사를 다시 계산해, 거부되는 경우에만 경고를 표시합니다. 승인된 사전은 승인 revision으로, 승인 전 사전은 지금 승인할 때의 revision으로 계산하며, 다시 계산하지 못하면 그 사실을 표시합니다. 실행 상세의 경고는 생성 당시 기준으로 남습니다. 반려된 사전과 이전 문서 버전의 사전은 다시 계산하지 않으며, 사전을 수정하거나, 추출 프롬프트·계약 버전·입력 예산이 바뀌거나, 요청 구성이 바뀌어 고정 표본 문서의 요청 크기가 달라지면 생성 때 기록한 경고도 표시하지 않습니다. 현재 문서 버전의 반려되지 않은 사전이면 이 기능 이전에 생성한 사전도 문서 화면에서 같은 방식으로 계산하며, 그 밖의 이 기능 이전 사전에는 경고가 없습니다. 경고가 없어도 승인 revision의 자릿수가 늘거나 입력 예산이 더 작은 다른 에이전트로 추출하면 거부될 수 있으며, 그때도 추출은 첫 호출 전에 거부되고 상세에 다음 단계를 표시합니다. 계산이 실패하거나 검사 기록을 저장하지 못하면 실행 상세에 그 사실을 표시하고, 어느 경우에도 사전 생성은 실패하지 않습니다.
- `data/runs/<id>/context-policy.json`에 등록 시 표 전환 기준을, 호출 폴더의 `context-budget.json`에 일반/표 정의 바이트·전체 요청 바이트·선택한 형식·실제 입력 예산을 기록합니다. `status`는 두 기준을 모두 만족하면 `within_limit`, 전송한 형식의 정의가 전환 기준만 넘으면 `over_context_limit`, 전송하지 못한 요청은 `unfit`입니다. 추출이 호출 전 검사에서 거부되면 상세에 표시한 청크에만 `unfit` 기록을 남기며, 예산을 넘는 다른 청크에는 기록이 없습니다. 모델 토큰 수용 한도는 확인되지 않은 경우 그대로 미확인으로 남깁니다. 저장 원문·사전·해시·승인 절차는 바꾸지 않습니다. 사전 생성이 성공하면 `data/runs/<id>/extraction-admission.json`에 그 경고 문구(거부되지 않으면 없음), 계산한 사전의 해시와 입력 한도 검사 정책의 해시를 기록하며, 이 계산은 `context-budget.json`을 남기지 않습니다. 문서 화면의 재계산도 파일을 남기지 않습니다.
- 사전 생성은 기존 사전의 ID·명칭·타입·별칭·관계 정의를 보내되 이미 검증한 인용문은 문맥에서 제외합니다. 모델은 이번 원문의 구간 ID로 인용 범위를 지정하고, 앱이 원문을 정확히 복원한 뒤 이름·별칭·타입·충돌을 검증합니다. 검토 화면과 저장 사전은 기존처럼 실제 인용문을 표시합니다.
- 사전 원문은 문장·줄 경계를 우선하는 최대 4,000자 구간으로 나누며 누락·중복 없이 최대 64개까지 처리합니다. 작은 구간은 호출 횟수를 늘릴 수 있고, 경계를 가로지르는 문맥·별칭의 한계는 남습니다. 이름·타입·별칭 대상·관계 설명/방향이 다르면 조정 제안으로 검토하며, 충돌만으로 전체 생성을 멈추지 않습니다. 동일 정의에 유효한 인용만 다르면 검증 후 첫 인용을 유지하며 중복을 합칩니다. 자기 자신을 가리키는 별칭은 대상 개체의 선언과 해당 ID를 포함한 원문 근거를 확인한 뒤 제외합니다. 실제 별칭에는 별칭과 정규 명칭이 함께 있는 근거가 계속 필요합니다. 관계의 타입은 기존·신규 개체의 `type` 값과 정확히 일치해야 하며 상위 타입을 자동 추론하지 않습니다. 생성 프롬프트에서도 이 제약과 예시를 안내합니다. 직접 사전 수정·승인에서는 선언되지 않은 타입·잘못된 형식·크기 초과를 거부하며, 미선언 타입 오류에는 관계 ID·필드·문제 타입을 표시합니다. 자동 생성에서 미선언 타입을 사용하는 관계 후보는 아래 제외 정책으로 처리합니다. 조정 내역에는 기존 정의와 제안, 원문 근거 및 적용/보류 사유를 표시합니다.
- 관계의 `subject_types`·`object_types` 개수는 각각 경고 기준을 적용하며, 초과해도 **모든 타입을 보존하고 생성을 계속**합니다. 기본 기준은 20개이며 설정 파일에서 아래처럼 변경할 수 있습니다(1~200 정수, 서버 재시작 필요). 중복을 제거한 고유 타입 수로 비교합니다. 승인 전 사전은 현재 서버 기준, 실행 기록은 실행 당시 기준을 표시합니다. 형식 오류·미선언 타입·정의 충돌과 전체 크기 제한은 계속 검증합니다. 자동 생성의 미선언 타입 관계는 아래 정책에 따라 후보 전체를 제외하며 타입 일부만 잘라서 보존하지 않습니다.

- 사전 생성에서는 근거가 부족한 항목을 제외하고 다음 구간을 계속 처리합니다. 일반 개체·별칭·관계 행에서 `quote_ref`만 빠진 경우도 원문 근거를 추측하지 않고 `reference` 사유로 제외하며, 독립적인 정상 항목은 보존합니다. 다른 필수 필드 누락·추가 필드·잘못된 `quote_ref` 값과 `revisions` 형식 오류는 계속 실패합니다. 재시도 시 이전 필터 정책 v5의 검증된 복구 구간도 재사용할 수 있습니다. **앞서 추출한 사전도 잠정 초안**이므로, 이후 원문에 따라 모델이 기존 이름·타입·별칭 대상·관계 정의의 수정을 `revisions`로 제안할 수 있습니다. 변경 전 정의가 정확히 맞고 변경 후 근거·의존 항목까지 검증된 묶음만 적용하며, 개체 이름을 그 개체 ID와 띄어쓰기만 다른 표기로 바꾸는 묶음은 위의 기준에 따라 보류합니다. 동일 타입의 중복 개체를 명시적으로 별칭 연결한 경우 양쪽 이름의 근거와 기존 참조를 검증해 정규 개체로 통합합니다. 단, 사전에 남아 있는 두 표기가 공백만 다르면 통합하지 않고 별도 개체로 둡니다(대상 개체 자신의 ID와 이름 쌍은 이 비교에서 뺍니다). 확정하기 어려운 충돌은 기존 정의와 제안을 보류 내역에 남겨 처리를 계속합니다. 형식 손상·알 수 없는 별칭 대상·크기 제한·통신 오류는 여전히 실패합니다. 자세한 계약과 예시는 [사전 조정](docs/dictionary-reconciliation.md)을 참고하세요.
- 일부 항목을 제외한 사전도 **검토 대기**로 저장합니다. 사전과 실행 기록에서 직접·연쇄 제외 건수, 구간·항목·사유를 확인하고 원문과 비교·수정한 뒤 승인하세요. 제외된 개체·관계는 이후 추출에서 빠질 수 있습니다. 진행률 100%는 구간 처리가 끝났다는 뜻이며 모든 항목을 빠짐없이 수용했다는 뜻은 아닙니다.
- 제외 보고서의 상세는 최대 500개까지 표시하지만 전체 건수는 모두 집계합니다. 상세 생략·기록 미확인을 제외 0건과 구분하며, 저장 실패도 실행 상세에 표시합니다. 제외 기록은 복구 기록에 함께 들어가 재시도에서 누락·중복되지 않습니다. 이전 엄격한 검증 방식의 복구 기록도 원래 계약과 원문 검증을 통과하면 재사용합니다.
- 각 구간 검증이 끝나면 실행 폴더에 복구 기록을 저장합니다. 실패·취소 후 **같은 문서 버전·에이전트·모델로 사전 생성**을 다시 누르면 호환되는 최근 실패/중단/취소 기록(대기 중에 취소한 실행은 제외)을 재검증하고 완료 구간부터 이어갑니다. 현재 필터 정책은 v6이며, v5로 저장된 schema 3 기록은 나머지 계약·사전·원문·감사 내역을 재검증한 뒤 재사용합니다. v4 이하 또는 알 수 없는 정책의 schema 3 기록은 재사용하지 않으므로, 호환되는 다른 기록이 없으면 모든 구간을 다시 호출합니다. 이어받는 schema 1·2 기록은 이 규칙으로 다시 검사하지 않아, 그 기록이 이미 가진 공백만 다른 연결은 초안에 남을 수 있습니다. v5·v6로 저장된 schema 3 기록의 이어받은 구간도 `revisions` 이름 변경 보류 규칙으로 다시 검사하지 않으므로, 그 구간이 이미 가진 ID와 이름이 띄어쓰기만 다른 개체는 남고 검토 카드와 검토 창에 표시됩니다. 전체 요청 예산 때문에 거부된 실행은 이어간 뒤 같은 크기로 다시 거부됩니다. 모델 ID가 비어 있으면 같은 ‘기본 모델’ 설정으로 간주하므로 제공자가 기본 모델을 바꾸었는지까지 보장하지 않습니다. 소스·프롬프트·처리 방식이 바뀌거나 기록이 손상됐으면 새로 시작하며 이유를 실행 상세에 표시합니다. 단, 명시적으로 호환하는 이전 프롬프트와 schema 1·2의 기록은 사전·원문·제외 내역을 재검증한 뒤 이어갑니다. 이전 방식에서 재사용한 구간의 조정 내역은 미확인으로 표시합니다.
- 복구 기록은 검토 대상이나 승인이 아닙니다. 모든 구간이 성공해야 하나의 사전이 **검토 대기**로 저장됩니다. 실행 상세에 완료 글자 수, 재사용한 실행 ID와 새 호출 시도 수를 표시합니다. 사전·완료 위치·제외 및 조정 내역을 함께 저장한 뒤 진행률을 확정합니다. 이 복구 기록 저장이 실패하면 해당 구간을 확정하지 않고 중단하며, 다음 재시도에서 직전 완료 구간부터 이어갑니다. 선택적 진행 표시 파일의 저장 실패는 경고로 남깁니다. 문서/버전 삭제 시 해당 실행과 복구 기록도 정리됩니다.
- 재사용한 구간의 비용은 이전 실행에 남고 새 실행에 중복 집계하지 않습니다. 전체 완료 기록을 재사용하면 새 호출 시도는 0회입니다. 복구·사용량 파일이 없을 때는 0회로 추정하지 않고 미확인으로 표시합니다.
- 관계 추출은 청크당 주장 12개·사실 80개, 프롬프트당 UTF-8 120,000바이트와 연결 도구의 더 작은 예산까지입니다. 조건·부정·시점을 지우면 의미가 바뀌는 내용은 위키 설명으로 남기도록 요청합니다. 상태·구성요소 나열은 각 항목을 검토하도록 요청하지만 누락이 없음을 보장하지는 않습니다.
- 반려한 사전은 **반려한 사전 다시 생성**으로 새 초안을 만들 수 있습니다. 성공하면 같은 사전의 새 리비전이 검토 대기로 저장되며, 이전 내용·반려 이력·실행 기록과 기존 추출 결과는 보존됩니다. 실패하면 기존 반려 사전을 유지합니다. 생성이 끝나기 전에는 이 사전의 검토 상태와 내용을 바꿀 수 없습니다. 생성이 대기·처리 중이면 이 문서의 새 원문 버전 등록을 거부합니다. 등록을 받아들이면 호출 비용을 쓴 결과를 저장하지 못하기 때문입니다. 새 생성은 반려 결과의 복구 기록을 사용하지 않으며, 실패 후 재시도는 같은 반려 리비전에서 진행한 재생성 구간만 재사용합니다. 승인·보류·검토 대기 사전은 먼저 반려하거나 내용을 직접 수정하세요.
- 사전 수정은 다시 검토 대기가 됩니다. 내용 수정에서 새로 넣는 개체 ID·이름·별칭이 `entity:` 또는 `relation:`으로 시작하거나, 새 개체 ID에 줄바꿈이나 탭이 있으면 거부하며, **사전에 추가**도 이런 개체 ID·이름·별칭을 거부합니다. **타입 고치기**는 관계 허용 타입이나 개체 타입 하나만 바꾸므로 이런 행을 새로 만들지 않습니다. 개체 이름은 같은 이름의 행이 여럿일 수 있어, 저장된 개수보다 늘어나는 행만 새로 넣는 것으로 봅니다. 모델 사전 생성(재생성·체크포인트 재개 포함)은 이런 행을 제외하지 않고 저장하며, 이미 저장된 사전에 이런 행이 있으면 검토 카드와 검토 창에 표시하고, 이 행 때문에 승인이나 다른 내용 수정이 거부되지는 않습니다. 이 문서 버전에 대기·처리 중인 추출이나 사전 재생성이 있으면 사전의 수정·승인·보류·반려·승인 철회를 거부합니다. 대기 중인 실행은 같은 단계의 실행 자리나 같은 문서의 이전 실행 정리를 기다립니다. 무엇을 기다리는지는 실행 기록에 표시됩니다. 기다리려면 실행 기록에서 끝난 것을 확인한 뒤 다시 시도하세요. 기다리지 않으려면 실행 기록에서 이 실행을 취소하세요. 취소하면 바로 다시 시도할 수 있고, 다른 실행과 질문은 계속됩니다. 처리 중이던 호출은 끝날 때까지 계속되지만 그 결과로 사전 초안이나 위키·관계 후보를 저장하지는 않습니다. 취소 방법은 아래 **실행 취소**를 보세요. 다른 문서나 이전 버전의 사전, 위키·관계 후보 검토는 막지 않습니다. 질문도 거부하지 않지만, 질문은 별도 작업자 1개에서 처리하므로 문서 작업이 끝나기를 기다리지 않습니다. 새 문서 버전은 자체 사전 승인이 필요합니다.
- 기존 추출 문서에도 사전을 만들고 다시 추출할 수 있습니다. 같은 승인 사전 revision·추출 방식 버전의 성공한 추출은 한 번만 허용하며, 실패·중단은 재시도할 수 있습니다. 이전 방식의 성공 결과는 같은 승인 사전으로 개선된 방식의 재추출을 한 번 할 수 있습니다. 수정·재승인 또는 승인 철회·재승인으로 새 revision이 되면 다시 추출할 수 있습니다. 기존 결과와 승인 이력은 보존하고 새 후보를 추가합니다. 중복 후보와 오래된 승인은 검토자가 판정하세요. 사전 승인 철회는 이미 별도로 승인한 사실을 자동 철회하지 않습니다.
- 새 후보의 수동 사실 수정도 당시 사전으로 검증합니다. 관계 어휘를 바꾸려면 사전을 수정·재승인하고 새 후보를 추출하세요. 사전 도입 전의 기존 사실은 종전 수정 계약을 유지합니다.

업데이트 전 서버를 종료하고 데이터 폴더 전체를 백업하세요. 시작 시 `runs.stage`와 `runs.ontology` 열을 추가하며 기존 실행은 `legacy`로 보존합니다. 마이그레이션은 재실행 가능하지만 이전 프로그램의 위치 기반 INSERT는 확장된 스키마와 호환되지 않습니다. 이전 버전으로 되돌리려면 프로그램과 함께 업데이트 전 DB 백업을 복원해야 합니다. 기존 데이터에 사전 승인을 소급 생성하지 않습니다.


## 실행 취소

대기 중이거나 처리 중인 실행의 문서 상세 진행 영역과 실행 기록에 **실행 취소** 버튼이 나타납니다. 확인창에서 취소를 확정하면 서버는 확인창을 열 때의 상태와 지금의 상태가 같은지 확인하고, 달라졌다면 취소하지 않고 이유를 알려 줍니다.

- **대기 중인 실행**은 모델을 호출하기 전에 바로 `취소됨`이 됩니다. 확인창을 연 뒤 처리가 시작됐다면 취소하지 않고 처리 중인 실행을 취소할지 다시 확인합니다.
- **처리 중인 실행**은 먼저 `취소 중`이 됩니다. 이미 허용한 호출은 중단하지 않고 끝날 때까지 기다린 뒤, 새 호출 없이 멈추고 `취소됨`으로 바뀝니다. 그 호출의 비용은 줄지 않습니다. 기다리는 시간은 추출 청크(인용 보정 포함)가 최대 360초, 사전 생성 호출이 기본 600초까지입니다. 멈출 때까지 같은 문서의 다음 실행은 기다립니다. 다른 문서와 질문은 각 단계의 실행 한도 안에서 계속됩니다.
- 취소한 실행은 사전 초안이나 위키·관계 후보를 저장하지 않습니다. 대기 중에 취소한 실행은 모델을 호출하지 않았으므로 복구 기록이 없고 재시도 후보 8개에 들지 않습니다. 검증을 마친 구간의 복구 기록은 남고, 같은 조건으로 다시 실행하면 호환되는 최근 실패·중단·취소 기록 중에서 재사용할 수 있습니다. 사전을 고친 뒤 다시 추출하면 기준 사전이 달라져 재사용하지 않습니다.
- `취소 중`인 실행은 사전 검토와 새 원문 버전 등록의 거부 조건에서 빠지지만, 문서 삭제는 `취소됨`이 될 때까지 거부합니다. 멈췄다는 기록을 남기기 전에 서버가 재시작되면 그 실행은 `취소됨`으로 표시됩니다.
- 병렬 추출(Claude 정책, Copilot 동시 2)에서 취소하면 이미 허용한 호출의 응답은 청크 제한 시간 안에서 끝날 때까지 기다려 순서대로 검증하고, 취소 뒤 새 호출 없이 통과한 청크는 복구 기록에 저장합니다. 취소 뒤에 새로 인용 보정 호출이 필요해진 청크나 검증에 실패한 청크부터는 저장하지 않으며, 다시 실행하면 그 청크부터 호출합니다.
- 대기 중이거나 처리 중인 질문의 답변 영역에는 **질문 취소** 버튼이 나타나며, 확인창과 상태 확인은 실행과 같습니다. 대기 중인 질문은 모델을 호출하기 전에 바로 `취소됨`이 되고 호출 0회로 표시합니다. 처리 중인 질문은 먼저 `취소 중`이 되고, 이미 허용한 모델 호출이 끝날 때까지 기다린 뒤 새 호출 없이 `취소됨`이 됩니다. 그 호출의 비용은 줄지 않습니다.
- 취소한 질문은 답변을 저장하지 않습니다. 취소 요청 전에 허용한 호출로 만든 답변도 취소 요청 뒤에 저장할 차례가 오면 저장하지 않습니다. 이미 답변을 저장한 질문은 취소하지 않습니다.
- 질문은 한 번에 하나씩 처리하므로 처리 중인 질문이 멈출 때까지 다음 질문은 기다립니다. 실행은 계속됩니다. 멈췄다는 기록을 남기기 전에 서버가 재시작되면 그 질문은 `취소됨`으로 표시됩니다.

## OpenRouter 실행과 비용

설정 화면에서 OpenRouter를 기본으로 고를 때는 공백이 아닌 모델 ID를 입력하세요. 모델은 제공자별로 저장하고 추출·질문에서 작업별로 바꿀 수 있습니다. 키가 없어도 설정은 저장되지만 실행은 작업 등록 전에 거부됩니다. **키 설정됨**은 파일의 값 존재 여부일 뿐 인증·잔액·모델 접근 검사가 아닙니다. macOS에서도 기본 Library 경로에 파일이 없으면 `~/.config/verinote/config.toml`을 자동으로 읽습니다. 절대 경로인 `XDG_CONFIG_HOME`이 있으면 `~/.config` 대신 그 경로를 사용합니다. 특정 파일을 우선 사용하려면 `python -m verinote --config ~/.config/verinote/config.toml`로 명시하세요. 파일 편집 후에는 서버를 재시작해야 합니다.

원문·사전·질문 등 프롬프트는 OpenRouter와 라우팅된 모델 제공자에게 전달되며 과금될 수 있습니다. 앱은 고정 HTTPS endpoint에 `stream: false`와 초기 `max_tokens: 16384`를 보냅니다. 이 상한은 모델별 지원 한도나 충분한 응답 길이를 보장하지 않습니다. 사전 생성과 승인 사전 추출에서는 **고급 설정 → 이 작업의 토큰 한도 직접 설정**을 켜고 슬라이더로 요청당 2,048~65,536토큰을 선택할 수 있습니다. 선택하지 않으면 서버 기본값을 유지합니다. 추론과 실제 답변이 이 한도를 함께 사용하며 인용 보정에도 같은 값이 적용됩니다. 질문과 CLI에는 적용하지 않습니다. 모델별 지원 한도는 별도로 확인해야 하며 값을 높이면 시간과 비용이 늘어날 수 있습니다. 이는 문서 전체 비용 한도가 아닙니다. 한도를 바꾸면 기존 중간 결과를 재사용하지 못할 수 있습니다. 서버 관리자는 생성자의 `ExecutionOptions`로 기본값을 조정할 수 있습니다. 화면에서 시작하는 사전 생성·추출은 답변 목표 여유도 함께 설정합니다. 작업 등록 당시 agent/model/상한/단계별 timeout을 고정합니다. 기본 deadline은 사전 호출당 600초, 추출 청크당 360초, 질문 호출당 180초입니다. 명시적 override가 우선하되 추출은 360초를 넘기지 않습니다. 응답 본문은 기본 1 MiB, 메타데이터는 256 KiB로 제한합니다. JSON 텍스트 지시와 기존 로컬 검증을 사용하며 native tool calling이나 구조화 출력 옵션을 추가하지 않습니다.

답변 목표 여유는 총 한도의 절반과 8,192 중 작은 값이며, 추론 요청 예산은 나머지에서 최대 4,096토큰입니다. 기본 총 16,384에서는 답변 목표 8,192·추론 예산 요청 4,096입니다. 이 값은 검증된 최적값이 아닌 초기 정책입니다. `reasoning.max_tokens`와 `provider.require_parameters=true`를 보내 추론 제어를 지원하는 제공자를 요청합니다. 모델에 따라 숫자 예산이 추론 강도로 변환되므로 엄격한 숫자 제한·실제 답변 토큰 예약·답변 완성을 보장하지 않습니다. 지원되는 제공자가 없으면 실패하며 자동으로 보호 설정을 빼서 재호출하지 않습니다. 기존 API에서 `answer_reserve_tokens`를 생략한 요청과 과거 v1 작업은 기존 동작을 유지합니다. 보호 요청은 v2 작업으로 저장되어 정책이 다른 중간 결과를 재사용하지 않습니다. [OpenRouter 추론 제어 설명](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)을 참고하세요.

앱은 통신 실패를 자동 재시도하거나 모델을 교체하지 않습니다. 자연어 질문의 로컬 답변 검증 실패에는 위에서 설명한 한 번의 답변 보정이 적용될 수 있습니다. OpenRouter 자체의 기본 upstream 라우팅은 유지되며 실제 응답 모델은 요청 모델과 별도로 기록합니다. 잘림(length)·모델 한도 오류는 실패합니다. 모델 ID나 서버 상한을 수동 조정한 뒤 새 작업을 등록하세요. timeout·연결 단절은 원격 생성 취소나 미과금을 뜻하지 않고 수동 재실행에는 추가 과금될 수 있습니다. 사전 재개는 검증된 구간 재사용이며 출력 재현성 보장이 아닙니다. OpenRouter 계약 버전·상한·timeout이 바뀌면 checkpoint를 재사용하지 않고, 재사용한 과거 호출의 비용은 새 작업에 중복 계상하지 않습니다.

사용량은 모델 content가 아닌 API envelope를 근거로 합니다. 입력에는 캐시가, 출력에는 reasoning이 포함됩니다. 보고 비용은 **OpenRouter credits**, 설정 단가의 추정 비용은 **USD**로 구분하며 합산하지 않습니다. 미확인은 0이 아닙니다. 실패한 호출도 안전하게 확인한 사용량을 보존하며 계정 잔액·실제 청구액과 다를 수 있습니다. 원문과 안전 검사한 응답은 로컬 데이터/로그에 남습니다. 알려진 키의 일반·JSON escape 에코는 저장 전에 거부하지만 임의 인코딩, 같은 사용자·관리자·백업 접근까지 모두 보호하지는 않습니다.

실 API 검사는 기본 테스트/CI에서 수행하지 않습니다. 명시적으로 한 번의 합성 요청과 과금 가능성을 허용할 때만 저장소 루트에서 다음을 실행하세요. 키를 인자로 넘기지 않습니다. 이 절차는 `max_tokens=256`, 전체 60초, 고정 JSON 프롬프트 한 번이며 자동 재전송하지 않습니다.

```sh
python -m scripts.openrouter_smoke --allow-network --config ~/.config/verinote/config.toml --model openrouter/free
```

모델 ID의 사용 가능 여부와 가격은 제공자 상태에 따릅니다. 스크립트 성공은 작은 요청의 연결·응답 검증이며 16,384 상한이나 장문 추출 품질 검증이 아닙니다. [검증 기록과 한계](docs/verification.md)를 참고하세요.

에이전트 설정에서 CLI 제공자의 이름이나 선택 버튼을 클릭하면 설치된 CLI가 안내하는 모델 목록을 불러옵니다. 모델 ID 옆의 **사용 가능한 모델**에서 고르면 ID 입력란에 반영되며, **설정 저장**을 눌러 저장합니다. 빈 ID는 CLI 기본 모델입니다. 같은 제공자를 다시 클릭하면 목록을 갱신합니다. 목록에 없는 ID도 직접 입력할 수 있으며 조회 실패가 기존 입력을 지우지 않습니다. 목록은 CLI 버전·로그인 상태에 따라 달라지고 실제 실행 권한을 보장하지 않습니다. OpenRouter는 기존처럼 모델 ID를 직접 입력합니다. 모델 조회는 프롬프트를 전송하지 않으며, 설치된 CLI 제공자 모두 Windows와 POSIX에서 지원합니다.

### 추론 예산과 실제 사용량 확인

OpenRouter 사용량은 출력에 포함된 추론 토큰과 보고된 비추론 출력(출력−추론)을 구분합니다. 숫자가 모두 유효한 호출별 차이만 합산하고 확인된 호출 수를 표시합니다. 실패한 호출도 확인된 토큰·비용을 보존합니다. 추론 요청 예산보다 실제 보고량이 크면 실행 화면에 초과 관측을 표시하며, 보고가 없거나 모순되면 준수 여부 미확인으로 표시합니다. 비추론 출력은 완성된 답변 길이나 실제 예약량이 아닙니다.

`openrouter/auto`·`openrouter/free`는 실제 모델이 바뀔 수 있습니다. 반복적인 예산 초과나 length 종료가 있으면 명시적인 모델 ID를 선택하고 숫자 추론 예산 직접 지원 여부를 확인하세요. 이 앱은 모델 지원 여부를 조회하거나 모델을 자동 변경하지 않습니다. OpenRouter는 일부 모델에서 `reasoning.max_tokens`를 추론 강도로 변환할 수 있습니다. `provider.require_parameters=true`는 지원 제공자 필터이며 숫자 준수나 답변 여유 보장이 아닙니다. 자동 유료 재시도는 하지 않습니다. [공식 추론 문서](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens), [제공자 선택 문서](https://openrouter.ai/docs/guides/routing/provider-selection).

CLI 호출에는 선택적 `cli-timing.json` 진단 기록을 남깁니다. 측정 저장 실패는 추출 결과를 바꾸지 않으며 첫 stdout은 모델 추론 시작을 뜻하지 않습니다. [형식·읽기 함수·시간의 포함 관계](docs/cli-timing.md)를 참고하세요.

승인 사전으로 CLI 추출할 때는 별도 `extraction-timing.json`에 대기·복구 검증·청크 호출/검증/인용 보정·후보 등록 구간을 기록합니다. 재사용 청크의 과거 시간·비용은 새 실행에 합산하지 않습니다. [문서 시간 형식과 읽기 함수](docs/extraction-timing.md)를 참고하세요.

Claude는 동일 모델의 후속 요청에서 프로세스를 재사용합니다. 요청마다 `/clear` 완료를 확인해 문서·청크 간 대화 이력이 섞이지 않도록 합니다. 실패한 요청은 자동 재전송하지 않습니다. 지원 버전·종료 방법·단발 실행 선택은 [Claude 프로세스 재사용](docs/claude-worker.md)을 참고하세요.

## Ollama 로컬 모델

설정에서 **Ollama (로컬 API)**를 선택하면 로컬 `127.0.0.1:11434`의 설치된 모델로 사전 생성·추출·질문을 실행할 수 있습니다. 모델 ID는 필수이며 제공자 이름을 클릭해 설치 목록을 조회합니다. API 키가 필요하지 않습니다. [설정·고정 옵션·사용량과 제한](docs/ollama.md)을 참고하세요.

승인 사전 기반 관계 추출은 [손실 점검](docs/extraction-loss.md)을 함께 수행합니다. 원문 위치가 확인된 사전 불일치 후보를 별도 보존하고 관계가 0개인 구간을 문서당 최대 4회 보충 점검합니다. 추가 모델 호출 비용이 발생할 수 있으며, 실행 상세에서 미해결·미점검 구간을 확인해야 합니다. 이 점검은 추출의 완전성을 보증하지 않습니다.

큰 사전은 ID·이름·타입을 원래 문자열 그대로 담는 위치 기반 표(v2)로 전달합니다. 모델이 문자열 참조 번호를 ID로 오인하는 문제를 줄이기 위한 표현이며 응답의 사전 검증은 유지합니다. 반복 값이 많은 사전은 이전 방식보다 커질 수 있고, 일반 JSON과 표 모두 입력 한도를 넘으면 호출 전에 거부합니다.
